# 범용 C/C++ 컴파일 설정 기반 분석 — 가능성 점검

점검일: 2026-10-05. 상태: **가능성 확인, 제품 기능으로 통합하기 전 설계 검토 단계**.

## 결론

DOOM 3 전용 매크로 이름이나 클래스 이름을 분석기에 넣지 않고도, Clang이 원본 정의를 펼치고 함수의 실제 소속 타입과 고유 심볼을 제공하는 것을 확인했다. 같은 추출 절차를 OpenRCT2의 대표 구현 파일 3개에도 적용했다. 따라서 선택형 컴파일 설정 기반 분석을 추가하는 방향은 타당하다.

그러나 현재의 가능성 점검을 “모든 매크로·모든 게임 지원 완료” 또는 “DOOM 3 완전 분석”으로 표현하지 않는다. 실제 CLI·G-SI·대시보드에 아직 연결하지 않았다. 기본 분석의 기존 결과는 그대로 보존했다.

## 확인한 실제 결과

| 입력 | 범위 | 오류 진단 없는 파일 | 오류 진단 있는 파일 |
|---|---:|---:|---:|
| DOOM 3 `neo/game` 구현 파일 탐색 | 71 | 43 | 28 |
| 위 중 원본 `game.vcxproj`에 등록된 독립 컴파일 입력 | 69 | 43 | 26 |
| OpenRCT2 대표 구현 파일, 프로젝트 설정 반영 후 | 3 | 3 | 0 |

DOOM 3에서는 원본 헤더를 컴파일 문맥으로 읽었다. 본문 추출의 집계 대상은 선택한 구현 파일에 있는 정의이며, 헤더 inline 함수 전체·렌더러·엔진 전체의 집계가 아니다. 71개 파일에서 4,383개의 본문 정의를 얻었고 그중 4,239개는 헤더에 선언된 소속 타입을 식별했다. 이는 복구 결과·매크로 생성 함수도 포함한 수이며, 완전한 함수 개수나 정확도 수치가 아니다. 기존 추출 4,089개와 수가 다르다는 이유만으로 더 정확하다고 단정하지 않는다.

구체적인 근거:

- `physics/Physics_Player.cpp`: 오류 진단 0, 정의 66개. `CLASS_DECLARATION`과 `END_CLASS`의 실제 사용 위치를 기록했고, 생성된 `CreateInstance`, `GetType`의 소속을 `idPhysics_Player`로 식별했다. 매크로를 삭제하거나 빈 정의로 바꾸지 않았다.
- `script/Script_Interpreter.cpp`: 오류 진단 0. `idInterpreter::Execute`의 원본 위치 936~1835행과 소속 타입을 식별했다.
- `Player.cpp`: 파일 전체에는 이벤트 테이블 관련 오류 1개가 남는다. `idPlayer::UpdateFocus`의 4326~4565행과 소속 타입은 얻었지만 파일을 완료로 표현하지 않는다.
- OpenRCT2 `core/Guard.cpp`, `core/Path.cpp`, `core/String.cpp`: 각각 정의 10, 14, 47개. 세 파일 모두 설정 반영 후 오류 진단 0이며, 두 번 실행한 정의·매크로·진단 목록이 같았다. 전체 OpenRCT2 정밀 지원을 검증한 것은 아니다.

## 왜 프로젝트 설정이 필요한가

OpenRCT2 첫 탐색에서는 대표 파일 3개 중 2개에 진단이 있었다. `String.cpp`의 `std::min`에는 Windows 매크로 충돌이 있었고, `Path.cpp`에서는 저장소에 이미 포함된 `sfl/static_vector.hpp`를 찾지 못했다.

원본 CMake에 명시된 `NOMINMAX`, char8_t 설정, `src/thirdparty` include 경로를 반영하자 세 파일 모두 읽혔다. 이 과정은 게임 코드를 고친 것이 아니라 **프로젝트가 원래 요구하는 설정을 분석에 전달한 것**이다. 제품에서는 이 정보를 게임별로 하드코딩하지 않고 사용자가 제공한 컴파일 설정에서 읽어야 한다.

DOOM 3는 `_Common.props`, `_Game.props`, `_Debug.props`의 정의를 참고한 Windows 분석 설정을 사용했다. 현재 SDK에 맞춰 C++17을 사용했다. 원래의 오래된 게임 빌드 환경을 재현한 설정은 아니므로 빌드 성공·게임 동작을 보증하지 않는다.

## 남아 있는 제약

1. `gamesys/Callbacks.cpp`는 `Class.cpp` 함수 내부에서 include하는 switch 코드 조각이다. 독립 컴파일 입력이 아니다. `EndLevel.cpp`도 현재 `game.vcxproj`의 컴파일 입력에 등록돼 있지 않다. 폴더의 모든 `.cpp`를 무조건 독립 입력으로 취급하면 부정확한 오류를 만든다.
2. 일부 이벤트 등록 매크로는 서로 다른 클래스의 멤버 함수 포인터를 강제로 변환한다. 현재 Windows Clang 해석에서는 크기 차이 진단이 남는다. 매크로를 버리거나 진단을 숨겨 완료로 만들지 않았다.
3. `TypeInfo.cpp`는 include 전에 `private`, `protected`를 `public`으로 바꾼다. 현재 표준 라이브러리와 충돌하는 진단과 후속 오류가 발생한다. 실제 게임 버그라고 단정하지 않는다.
4. 컴파일 오류가 없다는 사실도 추출의 정확성·전체 실행 동작·결함 판정의 증명은 아니다. 의미 관계를 원본과 대조하는 테스트가 별도로 필요하다.

처음 받은 libclang 18은 현재 MSVC 표준 헤더의 버전 검사에 걸렸다. 검사를 끄지 않고 Clang 20.1.8로 교체해 점검했다. Python 바인딩은 20.1.5를 사용했다. 라이브러리·압축 해제 도구는 모두 추적 제외된 실험 폴더에만 받았고, 시스템 설치·환경 파일·프로젝트 의존성 설정은 변경하지 않았다.

## 권장 추가 범위와 마무리 기준

기본 분석은 유지한다. 추가 기능의 이름은 **컴파일 설정 기반 분석(실험적)**으로 두고, 설정이 있는 프로젝트에서만 선택한다. DOOM 3는 검증 사례 중 하나이며 전용 규칙을 추가하지 않는다.

첫 통합의 분석·점수 단위는 구현 파일로 한정한다. 헤더를 문맥으로 사용하고 실제 함수 소속·심볼·매크로 발생 위치를 함께 제공하되, 전체 헤더 본문이나 완전한 클래스 의존성 분석이라고 주장하지 않는다. 기존 클래스/파일 혼합 결과와 새 파일 단위 결과를 같은 실험으로 합치지 않는다.

추가를 마무리할 조건은 다음과 같다.

- 실제 `analyze` 명령에서 선택할 수 있고 필요한 설정이 없으면 이유를 안내한다.
- 원본 컴파일 설정으로 입력을 선택하고, 파일별 실패·부분 추출·누락을 결과에 표시한다.
- 서로 다른 매크로·헤더·조건부 컴파일을 쓰는 작은 정답 사례에서 소속·호출·CC·원본 위치를 확인한다.
- DOOM 3와 OpenRCT2의 위 대표 범위에 같은 기능을 적용하고 재실행 결과를 비교한다.
- 기존 기본 분석과 기존 105개 테스트가 유지된다.
- 새로운 방식의 G-SI를 산출하기 전 원시 지표와 source mapping을 검증한다. 오류 개수 감소나 함수 수 증가만으로 정확도 향상을 주장하지 않는다.

전면 컴파일러 교체, 모든 엔진·빌드 방식 자동 지원, 자동 코드 수정, 유료 AI 검증은 이번 첫 추가 범위에 넣지 않는다. DOOM 3의 남은 오래된 컴파일러 호환성을 모두 해결하는 작업도 완료 조건으로 삼지 않는다.
