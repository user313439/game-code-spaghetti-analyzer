# Advisor experience and casual game demonstration

User approved this design in chat. Execute in the current checkout; preserve prior changes and original results. No commits, branches, push, paid API calls or report replacement.

The workspace has three steps: 01 static analysis, 02 AI refactoring advisor, 03 AI modification results. The existing sandboxed report remains isolated but reports its content height to its parent, so the outer document owns vertical scrolling. A bottom call to action opens the advisor. Only messages from the bound report window can update the frame height.

Use the existing SVG logo everywhere. Default to light blue, with an upper-right dark toggle and persistent preference shared by main and workspace. Preserve explicit white URLs. Correct help-button hover and expanded states in response CSS without rewriting fixed reports.

Advisor copy uses polite Korean. Show the selected scope, existing structure/reason, recommended change, expected effect, and checks. Generate a proposal, then exact code preview, then apply only after approval. Display aligned original/modified code columns, changed lines, and collapsed unchanged context. On small screens retain side-by-side comparison with horizontal scrolling. AI text always uses textContent.

The result step begins with a grounded plain-language summary of changed scope, measured improvements and unchanged metrics. Expected effects are labelled separately from measured results. Numeric tables and source downloads follow. One primary game action prepares a registered demo if needed and launches the modified build; controls are in expandable help. Do not claim gameplay success from build or SI alone.

Compare three actual public casual game projects for presentation suitability, supported source language, build effort, license/assets, and meaningful refactoring scope. Prefer a non-gory space shooter if a real project is buildable. Preserve the Doom example as historical evidence and create a new demo folder/job. Select the strongest verified candidate, then perform real CLI advice/preview/apply, reanalysis, build and feasible behavior checks. Never alter a game just to force a lower relative SI.
