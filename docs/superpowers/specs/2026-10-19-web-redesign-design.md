# 웹 재설계: 엉킴 진단 → AI 처방 → 리팩토링 → 검증 (라운드 반복)

작성: 2026-10-19 · Claude Code · 사용자와 시안 D·E·F를 확인하며 확정한 내용

## 1. 무엇을 만드는가

이 프로그램은 **게임 코드에서 엉킨 곳을 점수로 찾고, 왜 엉켰는지 보여주고, AI와 함께 풀고, 풀린 뒤에도 게임이 잘 돌아가는지 확인하는 도구**다. 제안서의 문제의식(한 곳의 수정이 엉뚱한 곳에 버그를 만드는 회귀 버그)과 진행 계획(지표 → 정적 분석 → 시각화 → AI 리팩토링 가이드 → 실험·검증)을 하나의 사용 흐름으로 묶는다.

사용자는 네 단계를 차례로 지난다.

1. **소스 가져오기** — 공개 GitHub 주소·ZIP·폴더를 가져와 범위를 확인하고 분석한다.
2. **엉킴 진단** — 진단서(카드)와 스파게티 지도로 어디가 왜 엉켰는지 본다. 필요하면 **AI 처방**을 받는다.
3. **AI 리팩토링** — 처방대로(또는 직접 고른) 파일의 실제 코드 변경안을 원본↔수정본으로 비교하고 적용한다.
4. **수정 결과·검증** — 엉킴 총량과 함수별 변화, 검증 결과를 보고 수정된 게임을 실행한다. 원하면 **다음 처방**을 받아 2라운드로 이어간다.

현재 웹이 어색했던 원인은 (1) 중간보고서 시절의 연구용 단일 HTML 보고서를 틀 안에 끼워 넣고 AI 화면을 따로 붙인 두 프로그램 구조, (2) 연구 단서 문구가 먼저 보이는 정보 순서, (3) 제안서의 핵심 시각화인 의존 관계가 묻혀 있는 점이었다. 그래서 **서버의 분석·AI·빌드 기능은 재사용하고 화면은 하나의 디자인으로 새로 만든다.**

확정한 시안은 `docs/superpowers/mockups/2026-10-19-web-redesign/`에 보존한다 (D 진단, E 리팩토링, F 결과). 시안의 숫자는 OpenTyrian 실제 분석·10월 19일 실제 변경 기록이며, AI 처방 문구만 예시다.

## 3. 핵심 개념

### 3.1 G-SI는 "반 등수", 엉킴 총량은 "시험 점수"

G-SI는 분석 집합 안의 백분위 순위라서 **어디부터 볼지 고르는 데** 쓴다. 내 점수가 올라도 등수는 같을 수 있으므로(10월 19일 사례: setupMenu CC 115→109, G-SI 유지) 전체가 좋아졌는지는 별도의 절대 지표로 보여준다.

### 3.2 엉킴 총량 (처음 상태 = 100)

같은 프로젝트의 **처음 분석(라운드 0)을 기준**으로 다섯 절대값의 비율을 평균한다. 기준값이 0인 항목은 제외한다.

| 항목 | 정의 | 줄어드는 수정 |
|---|---|---|
| 순환 고리에 묶인 단위 수 | 크기 2 이상 강한 연결 요소(SCC)에 속한 단위 수의 합 | 연결 정리 |
| 단위 사이 연결 수 | 의존 그래프의 간선 수 | 연결 정리 |
| 매우 복잡한 함수 수 | CC > 20 인 함수 수 | 파일 안 정리 |
| 초과 복잡도 | Σ max(0, CC − 10) | 파일 안 정리 |
| 전역 상태 접근 수 | 단위별 GlobalState 원시값의 합 | 둘 다 |

`엉킴 총량 = 100 × 평균(현재값 / 기준값)`. 화면에는 총량과 항목별 전후를 함께 보여준다. 분석된 파일 집합이 기준과 다르면(파일 추가·삭제, 구문 복구 상태 변화) 비교 대상이 달라졌음을 표시한다. 서로 다른 프로젝트끼리 비교하는 점수가 아니다. 보고서에서는 "기준 버전 대비 절대 지표"로 정의한다.

### 3.3 처방 효과는 프로그램이 계산한다

AI는 숫자를 쓰지 않는다. 처방에서 "연결 정리"로 분류된 단위마다 프로그램이 의존 그래프에서 **해당 단위의 연결이 끊긴 경우(단위 제거)의 최대 순환 고리 크기**를 차례로 계산해 "지금 상태 43 → opentyr 정리 후 22 → + keyboard 정리 후 12"처럼 보여준다. 이는 **최대 기대치**이며 실제 변화는 적용 후 재분석으로 확인한다는 문구를 붙인다. 계산 결과 고리가 줄지 않으면 "⚠ 이 파일만으로는 고리 크기가 줄지 않습니다"를 표시한다. "파일 안 정리"는 고리 계산에서 제외하고 대상 함수의 CC·길이를 보여준다.

### 3.4 처방 대상 ≠ 실제로 손대는 파일

처방 대상(매듭)은 최대 5개다. 실제 변경은 매듭을 고치기 위해 **함께 수정되는 파일**과 **새 파일**을 포함할 수 있다. 예: OpenTyrian의 `opentyr.h`는 공용 자료형(JE_byte 등)과 몇 개의 선언을 함께 담고 있어 26개 파일이 이를 포함한다. 공용 자료형을 새 헤더로 옮기고 각 파일의 `#include` 한 줄을 바꾸면, 손대는 파일은 약 27개지만 각 1줄이고 게임 동작 코드는 바뀌지 않는다. 구조 계산상 순환 고리는 43 → 22개 단위로 줄어든다(공용 자료형 분리를 반영한 계산, 실제 값은 재분석으로 확인).

### 3.5 라운드

`처방 → 변경안 → 적용 → 재분석`이 한 라운드다. 다음 라운드는 **직전 라운드 수정본**을 기준으로 진단·처방·변경한다. 원본은 항상 보존된다. 사용자가 원할 때 멈추며, AI는 효과 큰 처방이 없으면 `done: true`로 답할 수 있다. 최신 라운드는 취소(현재 위치를 직전 라운드로 되돌림)할 수 있고 기록은 지우지 않는다.

## 4. 화면

공통: 상단 바(로고, `분석 기록 / 프로젝트명`, 네 단계 표시, 다크 모드 토글). 존댓말·짧은 문장. 해석상 주의는 기본 본문에서 반복하지 않고 "어떻게 계산하나요?"·"자세히" 같은 접힌 곳에 둔다. 실제 실패·부분 분석·재분석 필요는 숨기지 않는다. 주요 진행 버튼은 영역의 오른쪽 아래에 둔다. 오래 걸리는 작업은 단계 표시·진행 막대·경과 시간을 보여준다(완료 이력이 있을 때만 예상 시간).

### 4.1 ① 소스 가져오기·분석 기록

현재 기능(GitHub·ZIP·폴더, 범위·언어 확인, 분석 진행·취소, 기록 정렬·삭제·복원)을 그대로 유지하고 새 디자인으로 다시 그린다. 구현 단계에서 시안을 먼저 보여주고 확인받는다.

### 4.2 ② 엉킴 진단 (시안 D)

- 제목: 프로그램이 결과로 만든 한두 문장 (예: "52개 파일 중 11개가 심하게 엉켜 있고, 43개 파일이 하나의 순환 고리로 묶여 있습니다.")
- 요약 카드 4개: E등급 수, 순환 고리 크기, 연결 수, 가장 복잡한 함수
- **진단서 ↔ 스파게티 지도** 전환 (기본: 진단서)
  - 진단서: G-SI 순 카드(점수, 한 줄 설명, 지표 막대 5개, 가장 복잡한 함수). 클릭하면 펼쳐져 "왜 엉켰나요?"(지표를 문장+상위 %로), 복잡한 함수 5개, 부르는/불리는 파일(칩, "+N개 더 보기"로 전부 펼침·접기, 칩 클릭 시 지도에서 위치)이 보인다. 나머지 단위는 "나머지 N개 보기"로 펼친다.
  - 지도: 자유 배치/원형 배치, 보기 필터(전체 연결 / 순환 고리만 / AI 처방 주변), 휠 확대·드래그·맞춤, 마우스 올리면 그 단위의 연결만 강조(부르는 쪽 파랑·불리는 쪽 주황)하고 정보 말풍선, 클릭 고정 시 "진단서에서 자세히 보기". 처방 대상은 파란 고리와 순위 번호.
  - 한 줄 설명 문장은 프로그램이 지표에서 만든다(AI 아님). 예: 가장 큰 원인 지표 두 개와 최고 복잡 함수.
- 오른쪽 **AI 처방** 패널
  - 받기 전: 설명, AI에 보내는 내용과 크기(구조 요약 + 주요 단위의 선언부 일부, §6.1), 연결된 AI와 변경 링크, [AI 처방 받기]
  - 받는 중: 단계·진행 막대·경과 시간
  - 받은 후: 프로그램이 고른 제목(§6.3), 순환 고리 계산 막대, 처방 목록(순위·종류 태그·이유·계산된 효과), 조건부 "왜 점수 1위 ○○가 아닌가요?", "무엇이 좋아지나요?", [직접 고르기] [추천대로 진행 →], "받은 시각 · AI · 다시 받기"
  - 실패: 이유, [다시 받기] [AI 연결 바꾸기]. 진단은 계속 사용 가능
  - 저장된 처방이 현재 라운드 분석과 다르면 "이전 분석 기준 처방"으로 표시하고 다시 받기를 권한다.

### 4.3 ③ AI 리팩토링 (시안 E)

- 상단 **전체 요약**: 질문 4개(무엇이 문제인가요 / 왜 바꿔야 하나요 / 어떻게 바꾸나요 / 무엇이 좋아지나요)
- 3단 작업대
  - 왼쪽: 처방 대상 파일(변경/유지 태그, +/− 줄, 바뀌는 함수) → 그 아래 **함께 수정되는 파일 N개**(접힘, 파일별 바뀐 줄 수) → **새 파일**, 파일 사이 관계
  - 가운데: 선택 파일의 원본(왼쪽) ↔ 수정본(오른쪽) 비교. 공통 들여쓰기 제거, 긴 줄 줄바꿈, 새 파일은 오른쪽만
  - 오른쪽: 선택 파일의 AI 소견(역할 / 무엇이 문제인가요 / 왜 이렇게 바꾸나요 / 무엇을 바꾸나요 / 무엇이 좋아지나요 / 접힌 "영향을 받는 곳과 확인할 동작"). 함께 수정되는 파일은 한 줄 이유만
- 하단 고정 바: "N개 파일 · 함수 N개 수정 · 새 파일 N개 · +a −b줄 · 원본은 그대로 두고 사본에 적용합니다" + [변경안 다시 만들기] [이 변경안 적용하기 →]
- 만드는 중: 단계(코드 준비 → AI가 변경안 작성 → 변경 범위 검사 → 완료)·진행 막대·경과 시간·취소
- 적용을 누르면 ④로 이동해 진행 상태(사본 생성 → 재분석 → 비교 → 정리)를 보여준다.

### 4.4 ④ 수정 결과·검증 (시안 F)

- 제목은 결과로 고른다: 순환 고리가 줄면 "순환 고리가 a → b개로 줄었고, …", 아니면 "함수 N개가 단순해졌고, …". 부제는 이번 수정의 종류(연결 정리/파일 안 정리)를 설명한다. 게임 검증 문구("게임은 그대로 잘 동작합니다")는 빌드·동작 비교·직접 플레이가 기록된 경우에만 쓴다.
- **엉킴 총량** 카드(100 → x)와 항목별 전후 카드. 변화 없는 항목은 회색 "변화 없음"
- **라운드 기록**: 라운드별 엉킴 총량 막대/선(100 → 78 → 72), 라운드 선택 시 그 라운드의 변경 요약
- 함수별 변화 표(전후 CC·길이, 새 보조 함수 표시), 파일 점수 표(G-SI·원시 지표 전후, "G-SI는 순위라 위치가 같으면 유지" 한 줄)
- 검증 체크: 원본 보존 / 승인한 변경과 동일 / 다시 분석 / 빌드 / 동작 비교 / 직접 플레이 — 기록이 없는 항목은 "아직 확인하지 않음"으로 표시하고 체크하지 않는다. 각 항목 "자세히"
- 오른쪽 게임 카드(등록된 시연 게임만): 이름, 한 줄 소개, 접힌 조작 방법, 오른쪽 아래 [수정된 게임 실행 ▶], 진행 막대·경과 시간
- 하단: [진단 화면으로] [수정본 내려받기 (.zip)] [다음 처방 받기 →] (+ 최신 라운드 취소는 메뉴 안)

## 5. 아키텍처

### 5.1 서버 (FastAPI, 기존 `game_si/web`)

새 모듈:

- `diagnosis.py` — `metrics.json`·`scoring.json`에서 진단 데이터를 만든다: 단위 목록(점수·등급·원시값·프로젝트 내 백분위·부르는/불리는 단위·순환 고리 여부·상위 함수 5개·한 줄 설명), 그래프(노드·간선), 요약(E 수, 고리 크기, 연결 수, 최고 복잡 함수), 단위별 레버리지(제거 시 최대 고리 크기). 순수 함수 + 결과 캐시.

## 6. AI 계약

### 6.1 처방 입력 (코드 원문 대신 구조 요약)

- 단위별: 이름, 경로, G-SI, 등급, 원시 5지표, 부르는/불리는 단위 수, 순환 고리 여부, 레버리지, 상위 함수 3개(이름·CC·길이)
- 프로젝트: 단위 수, 순환 고리 크기·구성, 연결 수, 엉킴 총량 항목, 현재 라운드와 이전 라운드에서 이미 고친 내용
- 근거 발췌: G-SI 상위 10개와 레버리지 상위 10개 단위의 선언부 발췌(C/C++ 헤더 또는 C# 클래스·멤버 시그니처, 단위당 4KB 이하) — 예: `opentyr.h`가 공용 자료형 모음이라는 사실을 AI가 볼 수 있게
- 총량 상한 80KB. 화면에 실제 전송 크기를 보여준다.

### 6.2 처방 출력과 검증

```json
{
  "done": false,
  "files": [
    {"name": "opentyr", "kind": "link", "reason": "…니다.", "change_idea": "…니다.", "expected": "…니다."}
  ],
  "why_not_top": "…니다.",
  "benefit": "…니다."
}
```

- `files` 1~5개(`done: true`이면 0개 허용), `name`은 분석 단위에 정확히 존재하고 중복 없음, `kind` ∈ {link, internal}
- 길이: reason·change_idea 300자, expected 200자, why_not_top·benefit 400자 이하. 모든 문장은 "-니다" 존댓말로 끝남
- 위반 시 같은 연결로 **1회** 재요청(위반 내용을 알려줌). 다시 실패하면 처방 실패로 표시하고 진단은 그대로 둔다.
- 저장 시 분석 기준 해시(현재 라운드 `scoring.json`)를 함께 기록한다.

### 6.3 제목 문장 (프로그램이 선택)

고리 감소율 r = (기준 − 마지막 계산값)/기준. 연결 정리가 있고 r ≥ 0.5 → "N개 파일만 정리해도 순환 고리가 크게 풀립니다." / 연결 정리가 있고 0 < r < 0.5 → "N개 파일을 정리하면 순환 고리가 줄어듭니다." / 그 밖 → "(이 파일의 | N개 파일의) 복잡한 함수부터 정리합니다." `why_not_top`은 G-SI 1위 단위가 처방에 없을 때만 보인다. `done: true`이면 "지금 기준으로는 효과가 큰 처방이 없습니다"와 엉킴 총량을 보여준다.

### 6.4 변경안 확장

- 처방(또는 직접 고른) 대상은 기존처럼 전체 원문(파일당 180KB 이하, 발췌 규칙 유지)을 보낸다. C/C++에서 처방 단위는 구현 파일과 같은 이름의 헤더(예: `opentyr.c` + `opentyr.h`)를 함께 대상 파일로 본다.
- 함께 수정될 수 있는 후보 = 대상 단위를 부르는 단위들. 이들은 `#include`/`using` 영역과 대상 이름이 나오는 줄 주변만 발췌해 보낸다.
- 응답: 기존 `file_reviews`·`edits`에 더해 `companions: [{path, reason}]`, `creates: [{path, content, reason}]`
- 검증: 함께 수정되는 파일의 편집은 `companions`에 적힌 파일만, 파일당 바뀐 줄 6줄 이하, 발췌 범위 안. 새 파일은 3개 이하·20KB 이하·지원 확장자·소스 범위 안·기존에 없는 경로. 대상 파일 규칙(선언한 함수와 실제 수정 함수 일치, 새 보조 함수 static 등)은 유지.
- 적용 후 비교·재분석·엉킴 총량은 함께 수정된 파일과 새 파일까지 포함한다.

## 9. 시연 시나리오 (영상용)

1. 프로젝트 소개 → OpenTyrian 가져오기·분석
2. 진단서로 엉킨 파일 확인 → 지도로 전환해 순환 고리 보여주기
3. AI 처방 받기 → "공용 자료형 헤더를 나누면 고리가 크게 풀린다" 류의 처방
4. 변경안 비교(대상 1개 + 함께 수정되는 파일들) → 적용
5. 결과: 순환 고리·연결 감소, 엉킴 총량 하락, 검증 체크 → 수정된 게임 실행·플레이
6. (선택) 다음 처방 → 가장 긴 함수 나누기 → 엉킴 총량 추이 100 → … → …

처방과 변경 내용은 실제 AI 응답에 따르므로 위 3·6의 구체 문장은 실행 결과로 정해진다.

## 11. 결정해 둔 사항과 남은 확인

- 테마는 라이트 블루와 다크 두 가지로 한다(기존 화이트 테마는 정리).
- 글꼴은 Pretendard를 앱에 내장한다(약 2MB).
- 처방 효과는 "해당 단위의 연결을 끊었다고 가정한 최대 기대치"로 계산하고, 실제 값은 재분석으로 보여준다.
- 이 대화의 작업 규칙을 따른다: 커밋·push·학교 제출·유료 API 호출은 사용자가 따로 요청할 때만 한다. 실제 AI 처방·변경 요청(구독 사용량)도 실행 전에 확인받는다.
- 최종보고서 v3는 시연을 마친 뒤 별도 요청이 있을 때 갱신한다.

## 구현과 다른 점 (2026-10-20 독립 검토 반영)

- 진단 API는 `?round=n` 대신 `?revision=<수정본 id>`를 받는다(기본값 = 현재 라운드).
- 처방은 작업당 `prescription.json` 하나에 저장하고, 분석 지문으로 '이전 분석 기준'을 표시한다. 이전 처방 5개까지는 `history`에 남는다.
- 변경 개수는 전체 80개로만 제한하고 파일당 12개 제한은 두지 않는다(헤더 분리는 한 헤더에서 여러 블록을 옮겨야 함).
- 선언 정리(declarations)는 '옮기기만' 허용하도록 더 좁혔다. 새로 쓴 선언 줄은 지운 줄을 옮긴 것이어야 하고, 지운 선언은 다른 곳에 다시 있어야 한다. 새 헤더는 기존 `#include` 이름과 겹칠 수 없다.
- 되돌린 라운드는 새 라운드를 적용하면 `rounds.json`의 `discarded`로 옮긴다(파일은 그대로 남는다).
- 글꼴(Pretendard)과 d3는 내장하지 않았다. 외부 다운로드 없이 시스템 글꼴을 쓰고, 지도는 같은 힘 모델을 직접 구현했다.
- 취소(§4.3)는 변경안·처방 생성 중에 쓸 수 있다. 그 요청이 실행한 AI 프로그램만 종료하고(다른 작업·분석·게임 빌드는 그대로), 늦게 끝난 작업은 상태를 덮어쓰지 않는다. API 키 방식은 이미 보낸 요청을 되돌릴 수 없어 결과를 버리기만 한다. 적용(사본 생성·재분석)은 취소하지 않는다.
