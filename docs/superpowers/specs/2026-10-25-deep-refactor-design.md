# 한 번에 깊게 고치는 AI 리팩토링과 화면 개선 (2026-10-25)

## 배경

OpenTyrian 리허설(작업 `4a45047f…`)에서 처방 5개 파일을 한 번에 고르자 보낼 코드가 283KB로 한도(240KB)를 넘었다. 그래서 `tyrian2.c`, `game_menu.c`는 발췌만 전달됐고, AI는 "본문 일부라 큰 함수를 못 나눈다"(JE_main CC 375, JE_itemScreen CC 371)며 작은 중복만 정리했다. 결과는 JE_menuFunction 98→95 정도로 작았다. 처방 5개 중 3개가 헤더 분리('연결 정리')였는데, 정밀 분석(Clang)은 실제 사용 관계로 연결을 세므로 숫자에 거의 잡히지 않았다.

사용자 결정(10/25): 여러 라운드로 나누지 않고 **버튼 한 번으로 큰 결과**를 보여 준다. 시간은 조금 더 걸려도 된다. 큰 파일도 다룰 수 있어야 한다.

## A. 한 번에 깊게 (deep preview)

### 흐름

`POST /api/jobs/{id}/assistant {action: 'preview', strategy: 'deep', …}` — 화면은 항상 deep으로 보낸다. `strategy`가 없으면 지금의 단일 호출(공동 검토)을 그대로 쓴다(기존 API·테스트 호환).

1. **묶음 나누기** (`plan_groups`)
   - 연결 묶음: 처방에서 `kind = link`인 선택 단위들. 지금의 공동 프롬프트로 한 번 부른다(헤더·#include·새 헤더·함께 수정 파일).
   - 함수 작업: 나머지 선택 단위마다 하나씩. 보내는 것은 그 파일과 짝 헤더이며, 짝 헤더는 읽기 전용이다. **고칠 수 있는 파일은 그 단위 파일 하나뿐**이다(새 static 보조 함수 포함).
   - 묶음이 하나뿐이면 지금과 같은 단일 호출이 된다(예산만 새 기준).
   - 함께 수정 후보(companions)에서 다른 묶음이 맡은 파일과 그 짝 헤더를 뺀다. 그래야 묶음끼리 같은 파일을 고치지 않는다.
2. **보내는 양** (호출마다 따로)
   - 호출 하나의 소스 합계가 `FULL_LIMIT`(300KB) 이하면 통째로 보낸다.
   - 넘으면 focused로 보낸다. 대상 함수(처방이 지목한 함수 → 없으면 CC 상위 함수)는 **본문 전체**를 넣는다(함수 하나 최대 200KB). 나머지는 지금처럼 발췌한다.
   - 프롬프트 상한은 호출당 `MAX_PROMPT_BYTES` 400KB.
   - `MAX_FILE_BYTES` 180KB → 1MB. 읽기·검사·적용의 상한이고, 보내는 양은 위 예산이 정한다.
3. **함수 작업 지시(deep guidance)**
   - 대상 함수의 전체 본문이 주어진다.
   - 의미 단위로 static 보조 함수를 뽑아 분기 수를 크게 줄인다. 동작·순서·전역 상태 변경·저장 형식은 그대로 둔다.
   - targets는 반드시 적는다. 다른 파일은 고치지 않는다.
4. **동시 실행**
   - 묶음을 모두 동시에 시작한다(선택은 최대 5개라 최대 5~6 호출).
   - AI 프로그램 오류(종료 코드·한도·시간 초과)로 실패한 묶음은 다른 묶음이 끝난 뒤 한 번 더 순서대로 시도한다.
   - 검사 거절은 다시 시도하지 않는다.
   - 호출 하나의 제한 시간은 900초(지금 600초)다.
   - API 연결의 출력 상한은 8,000 → 32,000 토큰, 시간 제한은 180 → 900초로 올린다.
5. **검사** (묶음마다, 지금 규칙 그대로)
   - `validate_scope`(그 묶음의 파일만)
   - `validate_target_methods`
   - `validate_edit_context`(그 묶음의 프롬프트)
   - 함수 작업은 자기 파일만 고쳤는지 확인
   - 원본 지문이 그대로인지 확인
   - `preview_changes`
   - `validate_preview_targets`
   - 묶음끼리 고친 파일이 겹치면 거절한다(구조상 없어야 함).
6. **합치기**
   - 통과한 묶음의 미리보기 파일·file_reviews·relationships·companions·creates·edits를 합친다.
   - 전체 요약(overview)은 프로그램이 만든다. 제목은 처방 제목이 있으면 그것을, 없으면 "N개 파일을 한 번에 정리"를 쓴다.
   - problem·reason·change·expected_effect는 묶음별 문장을 `[파일] 문장` 줄로 이어 붙인다. 추가 AI 호출은 없다.
7. **부분 성공**
   - 하나라도 통과하면 변경안을 만든다. 거절된 묶음은 `preview_failures`에 (파일, 이유)로 남긴다.
   - 모두 실패하면 지금처럼 실패 상태로 둔다.
   - 거절 응답은 `assistant-rejected-<n>.json`에 보관한다.
8. **실패한 파일만 다시**
   - `{action: 'preview', strategy: 'deep', retry_of: <preview_id>, candidates: [실패 단위]}`
   - 기반 라운드·원본 지문이 같으면 그 묶음만 다시 만들어 기존 변경안에 합치고, 새 preview_id를 준다.
9. **상태 표시**
   - `state.workers = [{key, label, kind(functions|link), mode(full|focused), sent_kb, state(waiting|running|done|failed|retrying), error, seconds}]`
   - 화면은 파일별 진행 줄을 보여 준다. 예: "통째로 보냄 120KB", "함수 단위로 보냄".
10. **취소·적용**
    - 취소는 지금처럼 그 작업의 AI 프로그램을 모두 끈다(`cancel_owner`).
    - 적용은 바뀌지 않는다. 합친 preview, 모든 원본 지문, 승인 1회만 쓴다.

### 안전 규칙 유지

- 원본은 고치지 않는다. 승인한 변경만 사본에 적용한다.
- 함수 밖 추가는 설명·호출이 확인된 static 보조 함수만 허용한다.
- 선언 정리는 옮기기만 허용한다.
- 함께 수정 파일은 #include 줄만 고칠 수 있다.

### 검토 반영 (10/25, Codex Astra 읽기 전용 검토) — 위 A를 아래처럼 좁혀 구현한다

1. **기본 deep 경로는 '파일별 함수 정리'만 한다.**
   - 선택 파일마다 AI 한 번씩 부른다. 보내는 것은 그 파일과 짝 헤더이고, 짝 헤더는 읽기 전용이다.
   - 서버가 아래를 강제한다: `change_type=functions`, `creates=[]`, `companions=[]`, 그 파일만 수정.
   - link 공동 묶음은 deep에서 뺀다. 변경안 화면의 '변경 방식'에서 **파일 사이 연결 정리(기존 공동 호출)**를 따로 고를 수 있게 둔다.
   - 묶음 사이에 수정↔읽기 의존이 생기지 않으므로 합치기가 안전하다.
2. **대상 함수는 자르지 않는다.**
   - 대상(처방 targets → 없으면 CC 상위) 본문 전체를 먼저 예약하고, 파일 머리(선언)와 짝 헤더를 넣고, 남는 자리를 다른 함수로 채운다.
   - 함수 하나도 못 담으면 그 함수는 '너무 커서 보류'로 표시한다.
   - 직렬화한 실제 프롬프트 크기로 확인한다.
3. **취소와 소유권을 스레드마다 넘긴다.**
   - `run_id`와 `owned_by` 키를 각 작업 스레드 안에서 설정한다(스레드 로컬이므로).
   - 시작 직전과 결과 반영 직전에 소유권을 확인한다.
   - 상태 저장은 잠금 아래 한 곳에서만 한다.
4. **동시 실행과 시간 제한**
   - 동시 실행은 3개로 둔다(`DEEP_PARALLEL`).
   - **자동 재시도는 하지 않는다.** 실패한 파일은 '이 파일만 다시' 버튼으로 다시 시도한다.
   - 작업 전체 마감(25분)을 넘기면 남은 파일은 시작하지 않고 '시간 부족으로 건너뜀'으로 표시한다.
5. **결과 구분**
   - 빈 edits는 성공이 아니라 '바꿀 곳을 찾지 못함'으로 구분한다.
   - 큰 개선 여부는 적용 후 재분석한 CC로만 판단한다(결과 화면).
6. **합친 결과 규약**: 전체 요약은 프로그램이 만든다(검증 대상 아님). file_reviews는 경로 중복을 제거하고, edits는 이어 붙인다. 묶음마다 파일이 겹치지 않음을 assert한다.
7. **처방 targets를 변경안까지 전달한다**(`_prescription_prior`).

## B. 처방

- 단위마다 `file_kb`와 가장 큰 함수의 줄 수·CC를 넣는다.
- 처방 항목에 `targets`(대상 함수, 최대 3개, 빈 배열 허용)를 더한다. 옛 처방은 빈 배열로 읽는다.
- 지침을 보강한다.
  - 정밀 분석은 실제 사용 관계로 연결을 세므로, #include만 옮기는 처방은 숫자가 거의 바뀌지 않는다.
  - 숫자로 확인되는 개선(복잡한 함수 분리)을 우선한다.
  - 대상 함수를 이름으로 지목한다.

## C. 화면

1. **Codex 인식**
   - `%LOCALAPPDATA%\OpenAI\Codex\bin\**\codex.exe`(가장 최근 파일)와 VS Code 확장 경로를 찾는다.
   - 로그인 여부는 `codex login status`(종료 코드 0이면 로그인)로 확인한다. AI 요청은 하지 않는다.
2. **지도 필터**: 처방 전에는 'AI 처방 주변'을 비활성화하고 이유를 안내한다.
3. **카드 순위**
   - 접힌 카드의 막대 아래에 `상위 N%`를 작게 적는다. 상위 10% 이내는 강조색, 값 0은 `없음`.
   - 펼친 카드에는 `52개 중 2위 (상위 4%)`를 적는다. 같은 값은 공동 순위로 한다(진단 데이터에 `rank`를 추가).
4. **가독성**(변경안 요약, AI 소견, 파일 사이 관계, 처방 문장)
   - 4열을 2×2로 바꾼다.
   - 문장마다 줄을 나눠 목록으로 보여 주고 첫 문장은 굵게 한다.
   - 파일·함수·매크로 이름은 코드 칩으로 보여 준다.
   - '·'로 붙은 이름 목록을 나누고, 긴 단어는 줄바꿈되게 한다(넘침 수정). 내용은 줄이지 않는다.
5. **결과 화면 '코드가 이렇게 바뀌었습니다'**
   - `GET /api/jobs/{id}/rounds/{n}/changes`가 바뀐 함수마다 전후 함수 원문 diff를 준다(새 보조 함수 포함, C/C++는 tree-sitter, 그 밖은 파일 diff).
   - 첫 카드 아래에 가장 크게 줄어든 함수부터 나란히 보여 준다(높이 제한, 함수 탭).
