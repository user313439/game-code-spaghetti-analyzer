# 선택형 컴파일 설정 기반 C/C++ 분석 설계

상태: **2026-10-05 사용자 승인, 2026-10-08 승인 범위의 구현·실험·독립 검수 완료**. 기본 분석 유지 + 아래 선택형 추가 범위를 구현했다. DOOM 3는 등록 입력의 부분 분석이며, OpenRCT2 완료는 대표 3파일에 한정한다. 실제 브라우저 상호작용과 게임 빌드·실행은 미검증이다. Git 커밋·브랜치·푸시는 수행하지 않았다.

## 목표와 근거

게임별 매크로 치환 없이, 프로젝트의 실제 헤더·매크로 정의·컴파일 설정을 사용해 구현 파일 본문의 함수·소속·호출 정보를 추출한다. 근거는 [가능성 점검](../../cpp-precision-feasibility.md)과 `reports/verification-cpp-feasibility-2026-10-05.json`이다.

현재 기본 tree-sitter 분석을 교체하지 않는다. DOOM 3에서 Windows Clang 호환성 진단이 남는 26개 등록 입력을 게임별 예외로 숨기지 않는다. 새로운 방식을 넣는 이유는 무조건 완료 표시를 얻기 위해서가 아니라 **프로젝트 설정을 고려한 구조 정보와 진단을 제공하기 위해서**다.

## 대안과 선택

1. 기존 분석만 유지: 제출 안정성이 높지만 컴파일 문맥을 반영하지 못한다.
2. **선택형 Clang 추출기 추가**: 기본 결과를 유지하면서 여러 C/C++ 프로젝트가 같은 입력 형식으로 사용할 수 있다. 준비된 컴파일 문맥과 호환되는 Clang 라이브러리가 필요하다. 첫 추가로 선택한다.
3. 전체 분석기를 의미 기반 클래스 분석으로 교체: 다중 파일 클래스 집계·헤더 inline·지표·과거 검증까지 재설계해야 한다. 이번 추가에서는 제외한다.

## 입력과 실행 경계

- 정식 진입점은 기존 `python -m game_si analyze`다. 기능을 실험 스크립트에만 구현하지 않는다.
- `--cpp-backend tree-sitter|clang` 선택을 추가하고 기본값은 tree-sitter로 유지한다.
- Clang 선택 시 `--compile-commands`로 컴파일 데이터베이스를 받는다. 첫 버전은 공식 형식의 `arguments` 배열을 지원한다. `command` 문자열만 있는 입력·응답 파일·지원하지 않는 래퍼 형식은 명확히 거부한다. 셸 문자열을 실행하지 않는다.
- `--clang-library`로 호환 라이브러리 위치를 지정할 수 있게 한다. Clang Python 바인딩은 선택 의존성으로 분리한다. 기존 기본 설치에 강제 설치하지 않는다.
- 분석 대상 경로 안의 등록된 C/C++ 구현 입력만 선택한다. compile database와 입력 경로의 교집합이 없으면 실패한다. 동일 파일의 여러 구성은 첫 항목을 쓰고 선택한 항목과 나머지 항목 수를 기록한다. 모든 구성을 분석했다고 주장하지 않는다.
- 등록되지 않은 구현 파일은 누락 목록에 분리해 표시한다. 단순히 분석 실패 파일로 세지 않는다. 외부 라이브러리/시스템 헤더는 문맥으로 읽되 점수 대상에서 제외한다.
- 타깃·표준·include·define 등의 분석 옵션을 전달하고 출력·링크·빌드 동작 옵션은 제거한다. 플러그인 로드·셸 실행·응답 파일 등 부수 실행 위험이 있는 옵션은 거부한다. 원본 빌드 스크립트는 실행하지 않는다.

## 추출과 분석 단위

- **첫 버전은 구현 파일 기반 분석 단위**로 고정한다. 클래스별 전체 G-SI나 전체 헤더 본문 분석은 첫 범위 밖이다.
- 선택한 구현 파일에 위치한 함수·메서드·생성자·소멸자 정의를 추출한다. 다른 헤더에서 온 inline 본문을 해당 구현 파일의 함수로 중복 집계하지 않는다.
- 메서드의 실제 선언 타입, 정규 이름, 고유 심볼, 원본 파일·행 위치를 메타데이터로 보존한다. 네임스페이스·오버로드·매크로 생성 정의를 구분한다.
- 매크로로 생성된 정의에는 생성 여부와 호출 위치를 표시한다. 원본 한 줄의 매크로 호출을 완전한 함수 본문처럼 AI에 전달하지 않는다.
- CC는 현재 C/C++ 계산 규칙을 명시적으로 맞추되, 해당 컴파일 구성에서 활성화된 본문을 기준으로 한다. 조건부 컴파일·매크로 확장 때문에 달라지는 값을 기록한다.
- 직접 호출은 해석된 심볼을 사용하고 동적 호출·외부 미해결 호출은 별도 한계로 기록한다. 현재 메트릭 엔진의 선택적 `symbol_id`, `invoked_symbols`를 활용한다.
- 파일 간 관계는 선택 범위의 본문 정의에 대응하는 직접 호출과 타입 참조를 사용한다. 타입 선언이 헤더에 있고 구현이 여러 파일로 분산된 경우 구현 파일 집합으로 매핑하는 **파일 관계 근사**임을 표시한다. 완전한 클래스 의존 관계라고 표현하지 않는다.
- 전역/정적 상태는 해석된 변수·정적 멤버 참조를 사용한다. 실행 중 실제 공유 상태 변경을 완전히 추적했다고 표현하지 않는다.

## 결과·오류 처리

- 기존 AST/메트릭/점수/HTML 흐름을 재사용하고, backend·선택 구성·포함/누락 범위·경고를 저장한다. 새 모드 출력은 기존 결과와 다른 폴더에 저장한다.
- 오류/fatal 진단이 있는 입력은 부분 분석으로 처리하고 복구된 정보의 불완전성을 표시한다. 경고는 표시하되 그 자체만으로 실패를 확정하지 않는다.
- 라이브러리 누락·설정 오류·유효 입력 없음은 실패로 안내한다. 자동으로 기존 방식에 바꿔 실행한 뒤 Clang 성공이라고 표시하지 않는다.
- 파일별 추출은 제한 시간과 프로세스 격리를 적용한다. 네이티브 파서 충돌·시간 초과는 해당 입력의 실패로 기록하고 나머지 입력을 보존한다.
- 기존 정상/부분/실패 종료 코드와 저장 실패 안내를 유지한다. 기존 `syntax_files`와 컴파일러 오류 입력 수를 같은 의미로 혼용하지 않는다.
- 점수는 구성·범위 내부의 상대적 우선순위다. 기본/Clang 점수 차이를 절대 품질 개선이나 정확도 향상으로 표시하지 않는다.
- `score-full`, 과거 시계열, 튜닝은 새 입력 모드로 자동 확장하지 않는다. 분석 방식이 다른 결과를 기존 검증에 섞지 않는다.

## 예상 변경 위치

- 추가: `game_si/clang_analyzer.py` — compiler context 처리·격리 추출·기존 AST 스키마 어댑터.
- 수정: `game_si/cli.py` — 선택 옵션과 명령 실행 연결.
- 수정: `game_si/diagnostics.py` — 구성 범위·컴파일러 경고/오류 구분.
- 필요한 경우 작은 수정: `game_si/report.py` — 분석 방식·선택 범위·누락 안내. 레이아웃 전면 변경은 하지 않는다.
- 선택 의존성: `pyproject.toml`. 환경 파일·비밀·락파일은 변경하지 않는다.
- 추가: `tests/test_clang_analysis.py` 및 작은 C/C++ fixture, 설정 기반 분석 사용 안내와 별도 검수 기록.
- 기본 `cpp_analyzer.py`, G-SI 공식, C# 분석기, 기존 결과는 보존한다. 메트릭 엔진 변경이 필요하면 기본 경로를 바꾸지 않는 선택적 심볼 필드 범위로 제한한다.

## 검증과 종료선

1. 헤더 선언 + 구현 분리, 다른 이름의 함수형 매크로 2종, 조건부 분기, 네임스페이스·오버로드를 가진 작은 정답 소스로 소속·원본 위치·직접 호출·CC·파일 관계를 검증한다. C와 C++ fixture를 모두 포함한다.
2. 미지원 command 형식, 플러그인 옵션, 라이브러리 누락, 외부 헤더 누락, syntax/semantic error, 네이티브 프로세스 실패, 제한 시간 초과, 빈 교집합, 결과 저장 실패를 테스트한다.
3. 실제 `analyze --cpp-backend clang`에서 DOOM 3 등록 구현 범위와 OpenRCT2 대표 3파일을 실행한다. 예제별 코드 이름을 추출기 안에 넣지 않는다.
4. 대표 함수의 행 범위·소속·CC·직접 호출을 원본과 대조한다. 함수 수 증가·진단 감소만으로 통과시키지 않는다.
5. 같은 입력·구성을 두 번 실행하고 시간/타임스탬프를 제외한 AST·메트릭·점수·상태의 재현성을 확인한다.
6. 기존 기본 분석 점수·메트릭·회귀 테스트가 유지됨을 확인한다. HTML의 상태·방식·내장 데이터·구문을 검사한다. 실제 브라우저 점검이 불가하면 별도 미검증으로 남긴다.
7. 범용 기능과 부분 분석 한계를 문서화한 뒤 추가를 확정한다. 그 이후 DOOM 3/OpenRA 시연 대상을 정하고 최종보고서를 작성한다.

DOOM 3의 69개 입력이 모두 컴파일러 오류 없이 처리되는 것은 이번 완료 조건이 아니다. 목표는 검증된 범위에서 의미 정보를 늘리는 선택형 기능과 정직한 실패 안내다. 추가 과정이 모든 과거 결과를 다시 설계해야 하는 수준으로 커지면 기본 버전을 확정하고 나머지는 향후 과제로 분리한다.
