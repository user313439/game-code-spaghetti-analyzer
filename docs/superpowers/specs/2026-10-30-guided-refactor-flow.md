# AI가 방법을 골라 단계적으로 진행하는 리팩토링 흐름 (2026-10-30 사용자 요구, 설계 초안)

## 사용자가 원하는 것

- 처음에 사용자가 방법(함수 나누기 / 선언 옮기기)을 고르지 않는다. AI가 진단을 보고 무엇부터 할지 정하고, 그 계획을 먼저 말한다.
  예: "함수 나누기부터 하고, 결과를 본 뒤 선언 옮기기가 더 도움이 될지 다시 판단하겠습니다."
- 순서를 정하기 애매하면 AI가 사용자에게 묻는다(어느 쪽이 나은지 이유와 함께).
- 한 단계가 끝나면 결과 화면을 바로 보여 주되, 더 좋아질 여지가 있으면 '끝'이 아니라 '진행 중' 화면이다:
  "이번 단계로 이만큼 좋아졌습니다. 선언 옮기기를 한 번 더 하면 더 좋아질 가능성이 있습니다." + [다음 단계 진행] [여기서 마무리].
- AI가 더는 좋아지지 않겠다고 판단하거나, 3단계에 닿거나, 사용자가 멈추면 '마무리' 화면: 빌드·직접 플레이를 앞세운다.
- 최대 3단계(그 이상은 원래 동작과 달라질 위험이 커진다는 사용자 판단).
- 다른 기법(함수 옮기기, 전역 변수를 매개변수로, 순환 끊기, AI 재작성)은 이번에 넣지 않고 보고서 '향후 과제'에 적는다.

## 지금 있는 것과 맞추기

| 필요한 것 | 지금 | 바꿀 것 |
|---|---|---|
| 방법 고르기 | 처방이 파일마다 change_type(functions / declarations)을 정함 | 처방 응답에 `plan` 추가: 단계 목록(최대 3, 단계마다 방법·이유·기대 효과), `order_certain`(false면 화면이 사용자에게 순서를 묻는다), 할 게 없으면 `stop_reason` |
| 한 단계 진행 | 라운드 1개 = 처방 → 변경안 → 적용 → 다시 분석 | 그대로. 단계 = 라운드 |
| 다음 단계 판단 | '다음 처방 받기' 버튼(사람이 누름) | 다음 처방 요청에 지난 계획과 단계별 결과(엉킴 총량 항목별 변화)를 넣고, AI가 계속할지·무엇을 할지·멈출지 답한다 |
| 결과 화면 | 단순안 목업 1종 | '진행 중'(다음 단계 안내 + 진행/마무리 버튼)과 '마무리'(빌드·플레이 앞세움) 두 모드 |
| 멈추기 | 없음(라운드를 안 하면 끝) | [여기서 마무리] 버튼: 계획의 남은 단계를 '사용자가 멈춤'으로 기록 |

AI 호출 수는 지금과 같다(단계마다 처방 1번 + 변경안). '다음 단계가 도움이 될지' 판단은 다음 처방이 맡으므로 따로 부르지 않는다.

## 화면에서 보일 말 (예시, OpenTyrian 10/26 결과)

- 처방 화면: "AI 계획 — 1단계 함수 나누기(가장 큰 문제: JE_main 1,712줄 등 거대 함수 8개). 1단계 결과를 보고 2단계 선언 옮기기(순환 고리에 묶인 파일 6개)를 할지 다시 판단합니다."
- 결과 화면(진행 중, 1/3): "큰 함수 8개를 작은 함수 52개로 나눴습니다. 다음 단계 제안: 선언 옮기기 — 파일 사이 순환 고리를 줄일 수 있습니다." [다음 단계 진행 →] [여기서 마무리]
- 결과 화면(마무리): "AI가 더 나눠도 효과가 작다고 판단해 여기서 마칩니다(이유: …). 이제 게임을 빌드하고 직접 해 보세요."

## 남은 결정 / 위험

- 단계 사이에 빌드·플레이를 할지(안전) 마지막에만 할지(빠름). 사용자 의견: 마지막에. 단, 빌드가 깨지면 어느 단계 탓인지 찾기 어려우므로 '진행 중' 화면에도 빌드 버튼은 작게 둔다.
- 실제 AI(Codex sol)로 2~3단계를 돌려 봐야 한다 — Codex 한도를 쓰므로 사용자 허락 뒤.
- 목업 먼저(키트 규칙): 처방 화면의 계획 표시, 결과 화면 두 모드.
