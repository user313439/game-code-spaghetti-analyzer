# AI가 방법을 골라 단계적으로 진행하는 리팩토링 흐름 (2026-10-30, 목업 확정)

목업: `design/mockups/guided-flow.html` (사용자 확인 2회 반영). 결과 화면 본문은 `result-screen-simple.html`(단순안)을 따른다.

## 흐름

처방(방법·대상) → 변경안 → 검사 → 적용 → 다시 분석 → **단계 결과** → (다음 단계가 있으면) 처방으로 돌아가 반복, 최대 3단계 → **마무리**(빌드 → 직접 플레이 → 완료).

## 정한 것

1. **처방 화면은 지금 형식 그대로**(먼저 정리할 함수 상자, 파일 목록, 무엇이 좋아지나요?, [추천대로 진행 →])에 '방법: …' 안내 한 칸만 더한다.
   - 필요한 방법만 보여 준다. 함수 나누기만 필요하면 선언 옮기기라는 말을 꺼내지 않는다.
   - 둘 다 필요할 때만 두 방법을 나란히 두고, 먼저 하길 권하는 쪽에 'AI 추천'을 붙여 미리 고른다. 사용자가 바꾸면 아래 파일 목록도 바뀐다. 고르지 않은 방법은 다음 단계에서 이어서 제안.
   - "여기서 마치기를 권합니다 / 왜 멈추나요?" 화면은 없다.
2. **효과가 없을 단계는 제안하지 않는다.** 프로그램이 계산한 기대 효과가 없으면 그 방법은 처방에 넣지 않는다.
   - 선언 옮기기는 연결을 `#include`로 세는 **기본 분석**(cpp_analyzer의 referenced_types)일 때만. 정밀 분석(Clang)은 실제 호출로 세므로 헤더만 옮겨서는 숫자가 바뀌지 않는다(10/25 실측: 연결 224 → 224, 고리 6 → 6).
3. **다시 분석이 끝나면 다음 처방을 자동으로 받아 둔다**(짧은 AI 호출 1번, 사용자가 멈추면 쓰이지 않음). 그래서 단계 결과 화면이 바로 '다음 단계 있음 / 여기까지'를 안다.
4. **단계 결과 화면**은 그 단계에서 바뀐 것만 보여 준다(단순안 본문). 맨 위에 '규칙 검사 통과 · 원본은 그대로 · 같은 기준으로 다시 분석' 칩. 효과 카드 2번 제목은 "함수 이름으로 찾아갈 수 있습니다"(예: 방어구 경고 → `updateLowArmorWarning`).
   - 맨 마지막 카드, 버튼은 오른쪽:
     - 다음 단계 있음: 무엇이 남았는지 + [여기서 마무리] [2단계 진행 →]. 2단계 진행 → 처방 화면으로, 여기서 마무리 → 마무리 화면으로.
     - 여기까지: "정리는 여기까지입니다" + 이유 한 줄 + [빌드하고 플레이해 보기 →].
   - '지금 빌드해 보기' 버튼은 두지 않는다(빌드는 마지막에 한 번).
5. **마무리 화면**(결과 화면과 따로): 제목 아래 '이번에 정리한 것' 한 줄(단계마다) + [단계 결과 다시 보기], 그 아래 빌드 → 직접 플레이 → 완료 진행 표시. '3단계 하지 않음' 같은 빈 단계 표시와 '한 단계 더 진행하기'는 두지 않는다.
   - 빌드: [게임 빌드하고 실행 ▶].
   - 직접 플레이: **확인할 동작 체크리스트**. 변경안 응답의 필수 칸 `checks`(파일마다 '확인할 동작')를 쓴다. 지금은 개발자 말("front-mounted 사이드킥 … 확인")이라, 스키마를 `{action: 플레이어 말, where: 게임의 어느 화면·상황}`으로 바꾸고 `where`로 묶는다(없으면 파일별로). 항목마다 '바뀐 곳: 파일 · 함수'. 체크는 선택. 버튼 [정상입니다] [문제가 있었습니다].
   - 문제 신고 창: 문제 종류(화면 이상·조작 안 됨·멈춤/꺼짐·소리·기타), 어디서(이번 확인 목록 + 어느 게임이든 같은 보편 항목: 켜질 때·처음 메뉴/설정·플레이 중·저장/불러오기·끌 때·잘 모르겠어요), 설명, 스크린샷(붙여 넣기·끌어 놓기·파일 고르기). 작업 폴더에만 저장. 기록 뒤 [관련 함수 전후 비교 보기] [이 단계 되돌리기(기존 라운드 되돌리기)] [다시 해 보기].
   - 완료: "정리를 마쳤습니다" + 정리 기록 카드(무엇이 좋아졌나 / 어떻게 확인했나) + [수정본 내려받기] [바뀐 코드 보기] [정리 기록 저장(카드를 이미지로)] + [다른 게임 분석하기].

## 서버 쪽 바뀔 것 (구현 메모)

- 처방 스키마에 `plan`: 방법 목록(최대 2: functions/declarations, 각각 이유·기대 효과·추천 여부), `stage`(몇 번째 단계), 다음 처방 요청에 지난 단계 결과(엉킴 총량 항목별 변화)를 넣는다. 할 게 없으면 빈 목록 + 이유 한 줄.
- 정밀 분석일 때 선언 옮기기를 처방에서 빼는 규칙(프로그램이 강제, AI 답에 있어도 버림).
- 적용·재분석 완료 뒤 다음 처방 자동 요청(단계 3 이후는 안 함).
- `checks` 스키마 변경(action·where), 플레이 기록·문제 기록(스크린샷 포함) 저장 API, 마무리 페이지.

## 확인 계획 (사용자 요청)

- 구현 뒤 **Codex로 테스트**: 문제 신고 흐름(기록·되돌리기·전후 비교)과 완료 화면의 '이제 무엇을 할까요?' 버튼이 실제로 동작하는지 꼭 확인. 실제 AI 호출·Codex 한도를 쓰므로 시작 전에 예상 사용량과 함께 사용자에게 묻는다.
- Codex 피드백 중 **제안(suggestion)은 바로 반영하지 않고** 사용자에게 쉬운 말로 "무엇이 어떻게 바뀌는지" 설명한 뒤 사용자가 정한다. 결함(버그)은 고친 뒤 알린다.
- 다른 기법(함수 옮기기, 전역 변수 매개변수화, 순환 끊기, AI 재작성)은 이번에 넣지 않고 보고서 '향후 과제'.
