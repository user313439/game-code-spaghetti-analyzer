# DOOM 3 추가 적용성 점검 (2026-10-05)

## 목적과 범위

작은 학습 예제 외에 실제 게임의 복잡한 소스에서도 기존 도구가 결과를 생성하는지 확인한다. 새로운 정확성·일반화 입증 실험으로 취급하지 않는다.

- 원본: https://github.com/id-Software/DOOM-3
- 고정 커밋: `a9c49da5afb18201d31e3f0a429a037e56ce2b9a`
- 입력: `benchmarks/DOOM-3/neo/game`
- 대상: 공개된 원작 게임플레이 C++ 구현. 렌더러·엔진 전체·확장팩·게임 데이터 전체의 분석이 아니다.
- `.cpp` 71개를 분석한다. 같은 폴더의 `.h` 64개는 현재 C/C++ 추출기의 본문 분석 범위에서 제외된다.
- 원본 코드는 수정하지 않았다. 다운로드한 외부 소스는 기존 `benchmarks/` 제외 규칙을 따른다. 게임 실행·빌드는 하지 않았다.
- 공개 저장소 README는 게임 데이터가 포함되지 않는다고 명시한다. 원본 저작권·라이선스 표기는 보존한다.

## 부분 분석의 원인 점검

52개 파일의 첫 진단 위치 중 41개가 `CLASS_DECLARATION`, `ABSTRACT_DECLARATION`, `EVENT`, `END_CLASS` 등 엔진 등록 매크로 위치였다. 이는 전체 오류 개수나 모든 구문의 원인 분류가 아니다. 나머지 첫 위치에는 `ID_INLINE`, 조건부 컴파일 분기, 포인터·타입 구문 등이 있었다. 진단을 DOOM 3 게임 자체의 버그로 해석하지 않는다.

`physics/Physics_Player.cpp`의 등록 매크로 블록 하나를 메모리에서만 제외하는 원인 확인 실험에서 tree-sitter의 `root.has_error`가 `true`에서 `false`로 바뀌었다. 원본 파일·분석 결과·점수는 이 실험으로 수정하지 않았다. 이 결과를 근거로 매크로를 일괄 삭제하거나 지원이 완료됐다고 주장하지 않는다.

전체 의존성·순환 참조·런타임 이벤트 연결은 특히 보수적으로 해석한다. `Game_local`의 큰 결합도는 구현 파일들의 공통 `Game_local.h` include를 파일 단위로 매핑한 영향이 있으며 실제 게임 클래스의 모든 의미 관계를 나타내지 않는다. 탐지된 순환 참조가 0이라는 사실도 전체 구조가 비순환이라는 증거는 아니다.

## 원시 복잡성 지표와 소스 대조

| 대표 구현 파일 | 본 도구의 파일 내 최대 함수 CC | Lizard의 파일 내 최대 함수 CC |
|---|---:|---:|
| `Game_local.cpp` | 41 | 41 |
| `Player.cpp` | 55 | 55 |
| `script/Script_Interpreter.cpp` | 193 | 192 |

클래스/파일 합성 단위 화면의 CC는 상위 10% 함수 평균이므로 위의 최대값과 혼동하지 않는다. 두 도구의 전체 정확성이 입증된 것은 아니며 위 표는 선택한 파일의 대조다. 본 도구는 switch의 default도 복잡성에 포함하는 규칙을 사용한다. `Execute` 함수의 default 분기도 확인했으며 계산 규칙 차이를 고려한다.

Lizard는 헤더까지 포함해 135개 파일을 읽었지만 비교의 일치 파일은 구현 파일 71개이다. G-SI와 Lizard 최대 CC의 파일 순위 상관은 0.7825, top-5 Jaccard 0.25, top-10 Jaccard 0.5385였다. 이는 두 목록의 관계이지 실제 결함 탐지 성능·AI 효과·유지보수 비용 감소의 검증이 아니다. 출력의 p=0을 정확한 확률 0으로 해석하지 않는다.

### 수동 소스 검토 예시 — AI API 출력 아님

`idPlayer::UpdateFocus`는 `Player.cpp:4326`에서 시작하고 CC 55로 계산됐다. 소스에는 NPC 대화 대상·차량·상호작용 UI의 탐색, 포커스 상태 전환, 인벤토리 정보 전달, HUD 변경이 함께 나타난다. 역할별 함수 분리는 검토할 수 있는 제안이다. 그러나 대상 탐색 순서, 가시선 판정, `break`·`continue`, 활성화/비활성화 이벤트와 상태 갱신 순서를 유지해야 하며 게임 실행 검증 없이 안전한 수정이라고 주장하지 않는다. 이번에 리팩토링을 수행하지 않았다.

`idInterpreter::Execute`는 명령 종류를 처리하는 큰 switch를 갖는 스크립트 인터프리터다. 높은 CC가 구조적 역할에서 비롯될 수 있으므로 무조건 분리·삭제할 대상으로 단정하지 않는다. 명령별 테스트와 동작 보존 여부를 먼저 검토할 필요가 있다.

## 현재 AI 보조 기능과 향후 방향

현재 `advise` 기능은 지표, 연결된 단위 이름, 선택한 가장 복잡한 함수의 앞부분 최대 30줄로 개선 제안을 요청한다. API를 호출하지 않는 입력 구성 점검에서 `Game_local`, `script.Script_Interpreter`, `Player`의 코드 조각이 생성되는 것을 확인했다. 세 후보 모두 함수 본문이 잘려 있었다. DOOM 3의 새로운 `advisor.json`은 생성하지 않았으며 유료 API 호출·비용 발생은 없다. 위 수동 검토를 자동 AI 결과로 혼합하지 않는다.

개선은 다음 순서가 적절하다.

1. 부분 분석 상태, 분석 단위, 누락 범위와 원시 지표를 AI 입력에 명시한다.
2. 선별한 후보의 함수 본문·필요한 타입 정의·직접 관련 호출을 제한된 예산으로 제공한다. 코드 일부만 받은 경우 판단을 보류하도록 한다.
3. AI가 제안한 이유·근거 위치·위험·검증 방법을 구분해 표시하고 사람이 확인한다.
4. 헤더·매크로·컴파일 설정을 고려하는 추출 방식은 별도 범위 확장으로 설계한다.
5. 자동 수정은 후속 목표다. 빌드·회귀 테스트·실제 게임 동작 검증 없이 개선 효과를 주장하지 않는다.

이번 DOOM 3 사례는 후보 탐색과 함수 복잡성 설명, 분석 한계의 사례로 사용할 수 있다. 완전한 엔진 지원이나 정확한 전체 의존성 분석을 보여주는 대표 시연으로 확정하기에는 부족하다. 기존 3게임 LOPO·bug-fix 상관·지표 제거 실험은 재실행하지 않았고 DOOM 3을 섞어 갱신하지 않았다.

## 재현과 검증

```powershell
git clone --depth 1 --filter=blob:none --sparse https://github.com/id-Software/DOOM-3.git benchmarks/DOOM-3
git -C benchmarks/DOOM-3 sparse-checkout set neo/game
git -C benchmarks/DOOM-3 rev-parse HEAD
# 위 해시가 기록된 고정 커밋인지 확인한다. 다르면 같은 입력으로 취급하지 않는다.
py -3.10 -B -m game_si analyze benchmarks/DOOM-3/neo/game --lang cpp --out reports/doom3-gameplay --project-name "DOOM 3 - gameplay source (neo/game)" --top 5
# 부분 분석 종료 코드 3이 정상적으로 예상되는 사례다.
py -3.10 -B -m game_si compare benchmarks/DOOM-3/neo/game --scoring reports/doom3-gameplay/scoring.json --out reports/doom3-gameplay --top-ns 5,10
```

전체 회귀 테스트 105개 통과, 생성 HTML의 부분 분석·접힌 도움말·내장 JSON·JavaScript 구문을 확인했다. 기존 소스/테스트 30파일과 기존 사례 산출물 40파일의 해시는 이전 검수와 같고, 첫 화면은 연도 표기 제거 후의 해시와 같았다. 실제 브라우저 클릭·시각 배치·게임 실행은 확인하지 않았다. 근거는 `reports/verification-doom3-2026-10-05.json`에 기록한다.
