# 로컬 분석 웹 프로그램

## 시작하기

프로젝트 폴더에서 Python 3.10 환경으로 한 번 설치합니다.

```powershell
py -3.10 -m pip install -e ".[web]"
py -3.10 -m game_si.web
```

브라우저에서 `http://127.0.0.1:8765`를 엽니다. 종료는 실행한 창에서 Ctrl+C입니다. 다른 프로그램이 포트를 사용하면 `--port 8766`처럼 변경합니다. 본인 PC에서만 접속하도록 실행되며 인터넷 공개 서버가 아닙니다.

2026-10-13 확인용 버전은 `http://127.0.0.1:8766/`에서 실행합니다. 창이나 PC를 종료한 뒤에는 서버가 계속 실행된다고 가정하지 말고 아래 명령으로 다시 시작합니다. 이번 확인은 8766 한 서버에서 진행하며, 같은 기록을 공유하는 여러 서버를 동시에 이용하는 방식은 지원하지 않습니다.

```powershell
$env:PATH = "C:\Program Files\dotnet;" + $env:PATH
py -3.10 -m game_si.web --port 8766
```

화면은 2026-10-20에 네 단계 흐름(소스 가져오기 → 엉킴 진단 → AI 리팩토링 → 수정 결과·검증)으로 새로 만들었습니다. 오른쪽 위 버튼으로 **라이트 블루/다크**를 바꾸며 선택은 이 브라우저에 기억됩니다. 예시 결과와 ‘원본 HTML 보고서 열기’로 여는 단일 HTML 보고서는 현재 테마에 맞춰 응답하지만, 파일 자체와 분석 수치는 바꾸지 않습니다. 이전 화면에서 저장한 `/workspace/<작업번호>` 주소는 새 진단 화면으로 이동합니다.

## 기본 사용 순서

1. **GitHub**: 공개 저장소 첫 화면의 주소를 입력하고 Enter 또는 **소스 가져오기**를 누릅니다. 프로그램이 기본 브랜치의 현재 커밋을 확인하고 소스 사본을 가져옵니다. 사용자가 미리 내려받을 필요는 없습니다. 이때 분석까지 자동 실행하지는 않습니다.
2. 또는 **내 파일**: ZIP 선택 / 폴더 선택 버튼을 누르거나 ZIP·폴더를 화면으로 끌어놓습니다. 폴더는 내부 상대 경로를 유지합니다. 폴더 끌어놓기를 지원하지 않는 브라우저에서는 폴더 선택이나 ZIP을 사용합니다.
3. 소스 가져오기를 누른 뒤 파일 수와 언어, 분석 대상 폴더를 확인합니다. 기본은 가져온 폴더 전체입니다. C#과 C/C++가 섞이면 폴더와 언어를 나눠 선택합니다.
4. **이 범위 분석하기**를 눌러 분석을 시작합니다. 실제 처리 단계·경과 시간과 접힌 진행 기록을 확인할 수 있습니다. 완료 또는 부분 분석이면 **엉킴 진단 보기**로 이동합니다.
5. **엉킴 진단**에서 진단서 카드를 눌러 왜 엉켰는지·복잡한 함수·연결된 파일을 보고, **스파게티 지도**로 바꿔 연결을 살펴봅니다(휠 확대, 드래그 이동, 마우스를 올린 파일의 연결 강조, 자유/원형 배치, 보기 필터).
6. 필요하면 **AI 처방 받기** → **AI 리팩토링**(변경안 비교·적용) → **수정 결과·검증**으로 이어갑니다. 자세한 내용은 [AI 사용·검증 안내](ai-refactoring-guide.md)를 봅니다.
7. **분석 기록**에서 새 분석과 실패·중단 기록을 다시 열고, 정렬·삭제·복원합니다. **예시 결과**는 기존 실험 자료이며 새 분석과 구분됩니다.

## 준비 조건과 제한

- 대상은 실행 파일이나 설치된 게임이 아니라 C#/C/C++ **소스 코드**입니다. 지원하지 않는 언어만 있으면 안내 후 중단합니다.
- C#은 기존 `csharp-analyzer`와 .NET 8 환경이 필요합니다. 웹 프로그램 자체가 .NET을 설치하지는 않습니다.
- 기본 C/C++ 분석은 컴파일 없이 구조를 추출합니다. 컴파일 오류가 없다는 뜻은 아닙니다.
- **정밀 분석(시연 게임)**: 가져온 소스가 이 앱에 준비된 시연 게임(OpenTyrian) 원본과 같으면, 범위 확인 화면의 ‘C / C++ 분석 방식’에 ‘정밀 분석 (Clang · 자동 인식된 빌드 설정)’이 기본으로 나타납니다(처음 보는 게임은 ‘기본 분석’과 ‘내 빌드 설정 직접 지정’만 나타남). 게임의 Visual Studio 프로젝트와 같은 컴파일 옵션(C17, SDL2 헤더, Windows 정의)으로 빌드 설정을 자동으로 만들며, 게임의 빌드 스크립트는 실행하지 않습니다. Visual Studio Build Tools·Windows SDK 헤더와 libclang(`GAME_SI_CLANG_LIBRARY` 또는 로컬 검증 폴더)이 필요하고 약 1분 걸립니다. AI 수정본도 같은 설정으로 다시 분석합니다.
- Clang은 고급 설정에서 C/C++를 명시하고 `compile_commands.json`, 필요시 libclang을 지정합니다. 업로드 사본은 기존 빌드 경로와 다르므로 **원래 소스 폴더 경로**를 함께 사용하는 편이 적절합니다. 원래 폴더를 지정하면 ‘원래 폴더 안의 분석 범위’가 적용되며 점(.)은 전체입니다. 이때 위에서 확인한 업로드 파일 수는 원본 파일 수를 보증하지 않습니다. 실제 결과의 분석 상태·등록·추출 수를 확인합니다.
- GitHub는 공개 저장소의 기본 브랜치만 지원합니다. 비공개 인증, 임의 사이트 주소, branch 페이지, Git submodule·LFS 원본의 자동 준비는 지원하지 않습니다. API 요청 제한·네트워크 문제에는 ZIP/폴더 입력을 사용합니다.
- ZIP 최대 100 MiB, 해제 데이터 최대 1 GiB, ZIP 항목 최대 20,000개입니다. 폴더 입력은 소스·헤더 최대 1 GiB / 20,000개입니다. 빌드 결과·의존성·환경 설정 파일은 가져오지 않습니다. ZIP의 전체 항목은 안전성 검사와 용량 계산에 포함되어 폴더 방식과 상한 적용이 다릅니다. 공개 GitHub 저장소는 묶음(tar.gz)을 받으면서 바로 풀어 소스·헤더만 저장하고 그림·소리 같은 리소스는 저장하지 않습니다. 묶음은 최대 2 GiB·15분, 저장되는 소스는 폴더 입력과 같은 1 GiB / 20,000개까지입니다.
- 한 번에 한 가져오기/분석만 실행합니다. 분석은 30분 제한입니다. 가져오기를 중단하면 다음 검사 지점에서 멈춥니다. 네트워크 응답을 기다리는 경우 최대 약 15초 뒤 반영될 수 있으며, 이전 처리가 종료되기 전에는 다음 작업을 차단합니다.
- 가져온 프로젝트의 실행·빌드 스크립트는 실행하지 않습니다. 입력 경로·링크·중복·손상 압축·용량을 검사하지만, 악성 입력에 대한 완전한 보안 샌드박스는 아닙니다. 신뢰할 수 있는 소스를 사용하고 외부에 서버를 공개하지 마세요.

## 저장 위치와 해석

새 입력·메타데이터·로그·결과는 `.cache/web/jobs/<작업번호>/`에 저장합니다. 기존 `reports/` 실험 자료를 덮어쓰지 않습니다. 기록은 이 PC에 보관되며 계정별 기록이 아닙니다. 캐시를 직접 삭제하면 기록도 사라지므로 필요한 결과는 따로 보관합니다.

분석 기록은 최신순·이름순·소스 크기순(큰 것부터)으로 정렬할 수 있습니다. ‘가져온 소스·헤더’ 크기는 성공적으로 가져온 분석용 파일의 합계입니다. ZIP 압축 크기, 결과 화면 크기, 이후 선택한 하위 분석 범위의 크기가 아닙니다. 가져오기가 실패했거나 용량을 확인할 수 없으면 ‘미확인’으로 표시하고 크기순 맨 뒤에 둡니다. Clang에서 원래 소스 경로를 사용해도 이 값은 가져온 사본 기준이며 실제 분석 범위는 결과에서 확인합니다.

쓰레기통 버튼으로 기록을 목록에서 삭제할 수 있습니다. 가져오기·분석 중에는 먼저 작업을 중단하고 실제 처리가 끝날 때까지 기다려야 합니다. 삭제 후 ‘되돌리기’ 또는 접힌 ‘삭제한 기록’에서 복원할 수 있고 프로그램을 다시 실행해도 복원이 가능합니다. 이 삭제는 캐시를 보존하므로 저장 공간을 확보하는 기능이 아닙니다. 삭제된 기록의 결과는 로컬 웹 주소에서도 열 수 없으며, 복원하면 다시 열 수 있습니다. 원본 게임 소스와 미리 제공한 예시에는 영향을 주지 않습니다.

화면의 ‘로컬 분석’은 외부 분석 서버가 아닌 이 PC에서 처리한다는 뜻입니다. 공개 GitHub 소스를 가져올 때는 인터넷을 사용합니다. 예시 결과는 OpenRA·Chocolate Doom·OpenRCT2·DOOM 3 프로젝트별로 소개하며, 같은 OpenRA의 세부 모듈은 접힌 보조 사례로 구분합니다. DOOM 3는 게임플레이 범위의 부분 분석 결과이지 전체 게임 분석 성공 사례가 아닙니다.

G-SI는 분석 집합 내부의 상대 검토 우선순위입니다. 작은 한 파일 샘플은 순위 비교에 적합하지 않습니다. 분석 완료 100%는 선택 범위의 처리 상태이지 전체 게임의 정확한 이해·버그 탐지율·빌드 성공률이 아닙니다. 부분 분석이면 진단 화면 위에 안내가 표시되고, 원본 HTML 보고서에서 원인과 한계를 확인할 수 있습니다. AI 처방·리팩토링·라운드는 [연결 방식·범위·검증 안내](ai-refactoring-guide.md)를 확인하세요.

## 직접 연습할 입력과 영상 순서

1. 빠른 조작 연습: [2048.c](https://github.com/mevdschee/2048.c) 주소를 입력하고 C / 전체 폴더 / 기본 분석으로 실행합니다. 콘솔 2048 게임의 작은 소스라 빠르게 결과를 확인할 수 있지만, 여러 파일의 순위·의존 관계 비교를 보여주기에는 적합하지 않습니다.
2. **대표 시연 권장: [OpenRA](https://github.com/OpenRA/OpenRA)**. 전체 폴더 / C# / 기본 설정으로 실행합니다. C# 파일 전체 범위에는 엔진·게임 모듈·도구·테스트가 포함되며, 다른 언어 1파일이나 자산·외부 라이브러리를 모두 해석한다는 뜻은 아닙니다. 2026-10-13 새 웹 실행에서 1,517개 파일, 3,287개 클래스, 11,674개 메서드, 순환 묶음 8개를 얻었고 파일 접근·추출 실패 및 구문 복구는 0개였습니다. 분석 실행은 약 28.34초(다운로드/사용자 선택 시간 제외)였으며 이 PC의 관측값입니다.
3. 부분 분석 설명용: [Chocolate Doom](https://github.com/chocolate-doom/chocolate-doom) 주소를 입력하고 C / 가져온 저장소의 `src` 하위 폴더 / 기본 분석으로 실행합니다. 폴더 목록에서는 `chocolate-doom-<커밋>/src`처럼 보일 수 있습니다. 현재 기본 브랜치를 가져오기 때문에 이전 고정 버전의 예시와 수치가 같아야 하는 것은 아닙니다.
4. 파일 입력 연습: 이전 실제 웹 검수에서 받은 `.cache/web/jobs/f371aca5f40d487ca96be56c52aab87a/repository.zip`은 2048 게임의 소스 ZIP입니다. ‘내 파일 → ZIP 선택’에 사용할 수 있습니다. 현재 PC에서만 있는 캐시 경로이므로 다른 PC에서는 공개 저장소의 소스 ZIP을 직접 준비합니다. 별도의 `demo-source.zip`은 인공 테스트 코드이므로 실제 게임 시연과 구분합니다.

DOOM 3는 유명한 복잡한 코드의 **부분 분석 사례 설명**에 적합합니다. 새 실행에는 원본 소스·호환 libclang·컴파일 데이터베이스가 필요하고 로컬 검수의 분석 시간은 약 3분 20초였습니다. 준비 없이 주소 입력만으로 정확한 Clang 분석이 된다고 설명하지 않습니다. 짧고 쉬운 실제 실행 영상은 OpenRA를 우선하고, DOOM 3는 별도 예시에서 분석 범위·오류 원인·원시 지표를 소개하는 구성을 권장합니다.

2026-10-11 실제 브라우저 검수에서는 Chocolate Doom 기본 브랜치 커밋 `895f581c5d91497bdda0516612da803fe5843e28`을 가져와 `src`를 분석했다. 분석 실행 관측 시간은 약 9.6초(다운로드 제외)였으며, 추출 296개·접근/추출 실패 0개·구문 복구 37개 파일로 ‘부분 분석’ 결과를 생성했다. 순위 표와 의존성 그래프가 열리는 것을 확인했다. 이 시간은 이 PC의 관측값이지 성능 보장이나 전체 게임 이해율이 아니다.

영상은 **주소 입력 → 소스 가져오기 → 언어·범위 확인 → 실제 분석 시작 → 결과 열기 → 원시 지표·검토 후보·의존 관계 → 분석 기록** 순서로 진행하면 됩니다. 기본 분석에는 API 키나 유료 AI 호출이 필요하지 않습니다. 실행 대기 구간은 ‘대기 화면 편집’이라고 밝히고 줄일 수 있지만, 사전 결과를 이번 실행 결과로 바꾸어 보여주지는 않습니다. 선택형 AI 시연은 공동 검토 → 파일별 판단 → 좌우 코드 검토 → 별도 수정본 적용 → 03 수정 결과로 이어집니다. 현재 OpenTyrian 게임 시연은 `docs/_demo_phase_v3/START_DEMO.cmd`에서 시작하며 자세한 순서는 같은 폴더의 `README_DEMO.md`에 있습니다. 이전 `_demo_phase_v2` 기록은 별도 보존합니다.

## 본인이 한 번 확인할 항목

에이전트의 자동 검사와 브라우저 조작 검수는 사용자 체험이나 설문이 아닙니다. 발표에 사용할 브라우저에서 아래를 한 번 확인합니다.

- OpenRA 주소 입력 후 Enter → C# / 전체 폴더 → 실제 분석 → 결과 열기.
- 결과표에서 클래스 이름 검색, CC/Coupling 설명 확인, 그래프에서 노드 정보 확인.
- 내 파일에서 ZIP 또는 폴더 선택. 끌어놓기 방식은 본인 탐색기·브라우저 조합에서 별도 확인.
- 이번 연습 기록만 삭제한 뒤 되돌리기. 삭제는 저장 공간 확보가 아니라 목록 숨김임을 확인.

문제가 있으면 **사용한 입력·선택 언어/폴더·화면 메시지·브라우저 이름**을 남깁니다. 실패한 실행을 완료로 설명하거나 예시 결과를 새 실행 결과로 대신하지 않습니다. 최신 검수와 남은 제출 단계는 [웹 최종 검수](web-final-review.md)에 정리합니다.
