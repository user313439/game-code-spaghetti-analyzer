Game Spaghetti Index (G-SI)는 게임 코드의 각 클래스가 다른 코드와 얼마나 얽혀 있는지를 0~100점으로 측정한 지표입니다. 점수가 높을수록 위험합니다.

등급 의미 → A 안전 · B 일반 · C 보통 · D 리팩토링 후보 · E 심각

💡 각 섹션 제목 옆의 「ⓘ 이 섹션이 뭔가요?」 버튼을 누르면 그 섹션이 무엇을 보여주는지 자세한 설명이 나옵니다. 화면 곳곳의 항목에 마우스를 올리면 그 자리에서 짧은 설명이 풍선으로 표시됩니다.

Project Health

이 프로젝트의 스파게티 정도를 한 숫자로 답하는 종합 점수입니다. 0~100 점, 점수가 높을수록 코드가 전반적으로 엉켜 있다는 뜻입니다.

다음 네 가지 신호를 가중 평균합니다.

  • 평균 G-SI (45%) — 프로젝트 안 모든 클래스의 G-SI 점수를 단순 평균. 가장 큰 비중.
  • 위험(D+E) 비율 (25%) — G-SI 60 이상(=D 등급 이상)인 클래스가 전체에서 차지하는 비율을 0~100 점으로 환산.
  • 순환 의존성 수 (15%) — A→B→C→A 처럼 서로 참조해서 빙빙 도는 묶음의 개수. 로그 스케일 적용(0 → 0점, 1 → 30점, 5 → 70점, 20 이상 → 100점).
  • 평균 결합도 (15%) — 클래스 한 개당 평균적으로 몇 개의 다른 클래스와 연결되는지(fan-in+fan-out 평균). 평균 10 이상이면 100점으로 saturate.

등급 기준은 다른 점수와 동일하게 A(0~19) · B(20~39) · C(40~59) · D(60~79) · E(80~100) 입니다. 발표 슬라이드에 "이 프로젝트는 C 등급(47점) — 평균 수준의 코드베이스" 같은 한 줄 요약으로 쓰기 좋은 숫자입니다.

Summary

분석 규모와 위험 신호를 6개 숫자로 압축한 카드 묶음입니다.

  • 분석 클래스 — Roslyn으로 파싱한 class · struct · interface · record · enum의 총 개수.
  • 분석 메서드 — 분석된 모든 메서드와 생성자(.ctor)의 합. enum 항목, 자동 속성은 카운트하지 않습니다.
  • 의존성 순환(SCC ≥ 2) — 크기가 2 이상인 강한 연결 요소(Strongly Connected Component). 적을수록 좋고, 0이면 의존성이 한 방향으로 흐른다는 좋은 신호입니다.
  • 평균 G-SI — 클래스 단위 G-SI 점수의 단순 평균. Project Health의 가장 큰 입력입니다.
  • 최대 G-SI — 이 프로젝트에서 가장 위험한 한 클래스의 G-SI. 보통 95~100점이 나옵니다 (percentile rank 특성상).
  • 위험(D/E) 클래스 — G-SI 60 이상인 클래스의 수. 변경할 때 영향 분석과 테스트 보강이 필요한 클래스들입니다.

등급 분포 및 가중치

왼쪽 등급 분포 차트는 프로젝트 안의 모든 클래스를 등급별로 나눠 비율을 보여줍니다. G-SI 점수는 프로젝트 내부의 분포에서 percentile rank로 계산하므로, 다섯 등급(A~E)이 각각 약 20% 씩 거의 균등하게 분포하는 것이 정상입니다.

이 차트가 의미하는 것은 절대적인 위험도가 아니라 "이 프로젝트 안에서의 상대적 위치"입니다. 다른 프로젝트와 직접 비교하려면 raw 점수 분포(평균 G-SI, 최대 G-SI 등)를 함께 봐야 합니다.

오른쪽 표는 G-SI 산식에서 각 항목이 어느 정도 비중으로 가중 평균되는지 정리한 것입니다. 각 항목 이름에 마우스를 올리면 무엇을 측정하는지 한국어 설명이 풍선으로 나타납니다. 본 작품은 default 가중치로 산식의 신뢰도를 확보하고, 후속 단계에서 데이터 기반 튜닝(--weights tuned) 옵션을 추가할 예정입니다.

Hotspot Table (G-SI 상위)

위험한 순서로 정렬된 클래스 목록입니다. 기본은 전체 클래스 중 G-SI 상위 N개를 보여주며, 두 가지 방법으로 표를 좁힐 수 있습니다.

  • 등급 필터 — A~E 중 하나를 선택하면 그 등급 안에서 다시 상위 N개를 골라 표를 새로 그립니다. "B 등급 안에서 가장 위험한 30개"처럼 봅니다.
  • 텍스트 검색 — 클래스의 정규 이름(FQN)이나 파일 경로 일부를 입력하면 일치하는 클래스만 남깁니다. 등급 필터와 동시 적용 가능합니다.

컬럼별 의미 — 헤더에 마우스를 올리면 각 컬럼이 무엇을 측정하는지 설명이 표시됩니다. 컬럼 헤더를 클릭하면 그 항목 기준으로 정렬됩니다(다시 누르면 역순). 우측 카운터는 "현재 보이는 행 수 / 조건을 만족하는 전체 / 프로젝트 전체"를 보여줍니다.

주요 원인 컬럼은 G-SI 점수에 가장 크게 기여한 두 항목을 알려 줍니다. 예를 들어 "cc, global_state" 는 그 클래스가 분기가 많고 전역 상태에 강하게 의존한다는 뜻입니다.

기본은 전체 클래스 중 G-SI 상위 30개를 표시합니다. 특정 등급(A~E)을 선택하면 그 등급 안에서 상위 30개를 다시 보여줍니다. 전체 등급 분포는 위 등급 분포 차트에서 확인하세요.

Dependency Graph (G-SI 상위 hotspot 중심)

위험 클래스 주변의 참조 관계를 점과 선으로 그린 그래프입니다.

  • 점(노드) = 클래스. 색은 등급(A 녹색 ~ E 빨강), 크기는 결합도(다른 클래스와 연결된 정도)에 비례합니다.
  • 선(엣지) = 한 클래스가 다른 클래스를 참조하는 의존성. 화살표 방향은 "이 클래스를 사용한다"의 방향입니다.
  • 표시 범위 — G-SI 상위 hotspot 부터 채우고 그 인접 클래스까지 포함하되, 노드 수가 최대 150개를 넘지 않도록 제한합니다. 그래서 작은 프로젝트는 그래프 전체가, 큰 프로젝트는 가장 위험한 영역만 표시됩니다.
  • A · B 등급 노드가 보이지 않는 이유 — 그래프 자체가 위험 클래스 중심으로 그려지기 때문에 표시 범위 안에는 거의 D · E 등급(과 일부 C)만 포함됩니다. A · B 클래스는 위 등급 분포 차트와 Hotspot Table 등급 필터에서 확인하세요.

Cycle Explorer (Strongly Connected Components)

A → B → C → A 처럼 서로 참조해서 빙빙 도는 클래스 묶음(Strongly Connected Component, SCC)을 모은 섹션입니다.

일반적으로 의존성은 한 방향으로 흘러야 합니다(예: UI → 로직 → 데이터). 그런데 두 클래스가 서로를 참조하기 시작하면, 한쪽을 수정할 때 반드시 다른 쪽도 함께 신경 써야 합니다. 이런 묶음이 3개, 4개로 커지면 영향 범위 추적이 사실상 불가능에 가까워집니다. 그래서 SCC는 리팩토링 1순위 후보입니다.

본 섹션의 카운트 카드 숫자가 곧 프로젝트 안의 모든 SCC 수입니다. 상위 N개를 보여주는 것이 아니라 전부 나열합니다. 프로젝트마다 수치가 다른데, 예를 들어 OpenRA.Game 모듈은 5개, OpenRA.Mods.Common 모듈은 4개의 묶음이 있습니다.

각 항목을 클릭하면 그 묶음에 속한 클래스 FQN 목록이 펼쳐집니다. 묶음 안의 모든 클래스가 동일한 SCC에 있다는 사실 자체가 이미 위험 신호이므로, 점수가 낮은 클래스라도 함께 정리 대상이 됩니다.

Module Summary

클래스 단위로 계산된 G-SI 점수를 최상위 폴더(모듈) 단위로 집계한 표입니다. "이 폴더 안 클래스들이 평균적으로 얼마나 위험한가"를 한눈에 봅니다.

컬럼 의미

  • 모듈 — 분석 입력 폴더 바로 아래의 1단계 폴더 이름. 예를 들어 OpenRA.Game을 분석하면 Network, Server, Map 등이 모듈로 잡힙니다. (root)는 폴더 안에 들어있지 않고 분석 폴더 바로 밑에 놓인 .cs 파일들을 한 모듈로 묶은 것입니다.
  • 등급 — 모듈 내 클래스 평균 G-SI를 기준으로 한 A~E 등급.
  • 평균 G-SI — 모듈에 속한 모든 클래스의 G-SI 평균. 모듈 전체의 위험도를 가장 잘 대표하는 값입니다.
  • 최대 G-SI — 모듈에서 가장 위험한 클래스 하나의 G-SI. 평균은 낮은데 최대만 높다면 그 모듈에 핀포인트 hotspot이 있다는 신호입니다.
  • 파일 수 · 클래스 수 — 모듈에 속한 .cs 파일과 클래스(struct, interface, record 포함)의 개수.

모듈 단위로 보면 어느 컴포넌트가 통째로 정리 대상인지, 아니면 특정 클래스만 문제인지 빠르게 판단할 수 있습니다.

  • 결합도 149 — 거의 모든 모듈(149개 클래스)이 이 기본 트레이트에 직접 의존하며, 이는 god-object 패턴 특성상 변경 시 연쇄 영향이 매우 크다.
  • 게임 루프 진입점은 아니지만(GameLoopCentrality=0), 조건 평가(`RequiredConditionsChanged`)가 trait 활성화/비활성화 상태를 관리하므로 모든 의존 trait 의 런타임 동작에 영향을 미친다. 이 메서드의 호출자가 프레임마다 실행될 가능성이 높다.
  • 정적 필드/싱글톤 접근이 3회 있어 테스트 격리가 어렵고, 작은 LOC(37줄) 대비 매우 높은 결합도는 기초 인터페이스로서 변경 위험이 비정상적으로 크다는 신호다.

리팩토링 방향

  • 현재 구조를 '변경 금지' 수준으로 안정화하라 — 이미 게임 아키텍처의 기초를 이루고 있어 리팩토링보다는 semantic versioning 과 명확한 계약(contract) 문서화가 우선이다. 새 기능은 상속이나 composition 으로 확장하는 방식을 선호한다.
  • 조건 평가(`Info.RequiresCondition.Evaluate`) 의 성능을 characterise 하라 — 이 메서드가 모든 의존 trait 마다 호출된다면 캐시 정책(평가 결과 memoization, 조건 변화 시에만 재평가) 을 검토해 프레임 성능에 미치는 영향을 추적한다.
  • `IsTraitDisabled` 상태 변화 시 콜백(`TraitEnabled`/`TraitDisabled`) 실행 순서를 검증하는 integration test 를 강화하라 — 조건 활성화/비활성화 경계에서 의존 trait 들이 일관된 상태로 전환되는지 확인해야 한다.
  • 정적 필드 3개 접근을 추적하고, 가능하면 trait 인스턴스 필드로 전환하여 테스트 시 mock 주입이 가능하도록 개선한다. 단, 게임 루프 핫 패스에서 성능 영향을 측정해야 한다.

테스트 우선순위

  • Characterisation test: 현재 `RequiredConditionsChanged` 메서드의 호출 빈도, 캐시/상태 전환 시 지연을 측정하고, 리팩토링 전후 프레임 시간(frame time) 및 GC 할당을 비교하는 성능 regression test 를 작성한다.
  • Golden master / state machine test: 조건 문자열과 평가 결과(`IsTraitDisabled`)의 모든 경계 케이스(null 조건, 빈 문자열, 복합 조건식 등)를 matrix 로 검증하고, 상태 전환 시 `TraitEnabled`/`TraitDisabled` 콜백이 정확히 한 번씩 호출되는지 확인한다.
  • 의존도 구조 regression test: 현재 149개 의존 클래스 목록을 '기대값'으로 기록한 뒤, 향후 변경 시 의존도 증가(또는 패턴 변화)를 감지하는 아키텍처 검사를 CI 에 추가한다. 이는 변경 범위를 조기에 경보한다.
불확실성: 코드 스니펫만으로는 정적 필드 3개의 구체적 위치와 의도를 확인할 수 없다 — 전체 클래스 정의와 초기화 코드를 검토해야 그 필드들이 정말 호출 경로의 병목인지 판단 가능하다. 또한 `RequiredConditionsChanged` 의 호출 빈도와 호출자(어느 trait 또는 시스템이 이벤트를 발생시키는지)를 추적해야 게임 루프 영향도를 정확히 평가할 수 있다. LOC 37은 작지만 결합도 149 라는 extreme value 는 이 클래스가 실제로 basic interface/marker trait 수준의 역할을 하는지, 아니면 데이터 구조가 불필요하게 복잡한지 구분이 필요하다.
#2EG-SI 100.0OpenRA.Mods.Common.Traits.ConditionalTraitInfoTraits/Conditions/ConditionalTrait.cs · 메서드 RulesetLoaded

위험 원인

  • 결합도 149 — 프로젝트 내 거의 모든 Trait 정보 클래스(149개)가 이 기본 클래스에 의존하며, 이는 'god-interface' 패턴으로 볼 수 있다. 이 클래스의 API 변경은 광범위한 캐스케이딩 변경을 초래한다.
  • 작은 본문(4줄)에도 불구하고 극도로 높은 결합도로 인해 변경 위험이 극대화되어 있다. 메서드 본신 CC는 낮지만(2.0), 이는 반복적인 trait 조합 패턴에서 안정적인 기초 타입이 필요함을 의미한다.
  • 조건부(Condition) 평가 로직이 게임 규칙 로딩 단계(RulesetLoaded)에 깊숙이 박혀 있어, 조건 시스템 전체의 의존성 그래프에서 중추 역할을 한다. 이 메서드의 동작 변경은 모든 AI 모듈, 트리거, 게임 기계(mechanism) 초기화에 영향을 미칠 수 있다.

리팩토링 방향

  • 이 클래스는 리팩토링 대상이 아니라 **API 안정화·버전 관리** 대상이다. 변경이 불가피할 경우 semantic versioning을 엄격히 지켜 하위호환성을 보장하거나, 새로운 기본 클래스를 도입하되 레거시 클래스와의 어댑터 계층을 제공한다.
  • 결합도 감소를 위해 EnabledByDefault 초기화 로직을 공유 유틸리티 함수(예: `EvaluateConditionDefault`)로 추출하고, 파생 클래스들이 명시적으로 호출하게 리팩토링할 수 있다. 다만 이는 149개 파생 클래스의 일괄 검토를 요구하므로, 먼저 가장 자주 변경되는 모듈(예: AI 관련) 일부에만 시범 적용한다.
  • 조건 평가 자체를 전용 Condition 클래스 또는 람다 기반 구조로 분리하여, ConditionalTraitInfo가 단순 플래그 저장소 역할만 수행하도록 단순화한다. 이는 조건 엔진의 유연성을 높이고, 이 클래스의 변경 빈도를 줄일 것이다.

테스트 우선순위

  • Characterisation test: 모든 파생 trait 정보 클래스에 대해 RulesetLoaded 호출 전후 EnabledByDefault 상태 변화를 기록하고, 회귀 감지용 golden master로 저장한다. 이를 통해 API 변경 시 영향 범위를 즉시 확인한다.
  • 조건 평가 로직 변경 시 영향도 테스트: RequiresCondition 파싱, VariableExpression.NoVariables 맥락, 기본값 설정 경로에 대한 파라미터화 테스트를 작성한다. 특히 null 조건(RequiresCondition == null)과 복잡한 조건식 평가의 경계 케이스를 검증한다.
  • 통합 테스트: 게임 규칙 로딩 단계에서 150개 이상의 파생 클래스가 동시에 RulesetLoaded를 호출할 때, 조건 평가 순서, 의존성 순환, 예외 전파가 올바르게 처리되는지 확인한다. 이는 게임 시작 안정성과 직결된다.
불확실성: 코드 스니펫은 메서드 본신만 제시되어 클래스 전체 구조(필드, 다른 메서드, 네임스페이스 컨텍스트)를 알 수 없다. EnabledByDefault 필드의 선언 위치, 다른 public/virtual 메서드의 존재 여부, 이 클래스가 중간 추상 기본 클래스인지 최상위인지 불명확하다. 또한 149개 fan-in 클래스 중 실제 변경 빈도와 함께 변경되는 비율을 알 수 없어, 리팩토링 비용-편익 산정이 정확하지 않다.
#3EG-SI 99.9OpenRA.Mods.Common.Widgets.TextFieldWidgetWidgets/TextFieldWidget.cs · 메서드 HandleKeyPress

위험 원인

  • Cyclomatic Complexity 98 — 메서드 `HandleKeyPress`가 거대 switch/조건문 구조로 되어 있으며, 60개 이상의 키입력 케이스를 처리하는 god-method 패턴. 이는 각 분기의 테스트 커버리지 확보를 어렵게 하고, 새로운 키입력 로직 추가 시 의도하지 않은 인터랙션 버그 위험이 높다.
  • GlobalState 56 — `Platform.CurrentPlatform` 같은 정적 싱글톤 상태에 직접 접근하는 빈도가 높다. 키입력 핸들러가 UI 위젯의 게임 루프 진입점(KeyboardFocus, IsDisabled 체크)에 속하므로, 전역 상태 의존성은 단위 테스트 격리를 방해하고 멀티스레드 입력 처리 시 경쟁 조건을 유발할 수 있다.
  • GameLoopCentrality 1.0 — `HandleKeyPress`는 입력 이벤트 처리의 게임 루프 직접 호출 메서드로, 매 프레임 또는 이벤트 발생 시마다 실행되는 핫 패스다. CC 98인 메서드가 핫 패스에 있으므로, 리팩토링 중 분기 추가·로직 재정렬은 입력 응답성과 fps에 즉시 영향을 미친다.

리팩토링 방향

  • 키입력 케이스를 키 코드별 dispatch 테이블(Dictionary<Keycode, Action<KeyInput>>)로 분해한다. 각 핵심 키(RETURN, TAB, ESCAPE, BACKSPACE 등)별로 개별 메서드(`HandleReturnKey`, `HandleTabKey` 등)로 추출하되, 플랫폼 분기(OSX vs 기타)는 조건부 등록 시점으로 미루어 `HandleKeyPress` 본문의 CC를 30 이하로 낮춘다. 이때 dispatch 테이블 구성 비용(메모리)은 한 번만 발생하므로 핫 패스 성능 영향을 최소화한다.
  • 정적 상태 접근을 클래스 생성 시점 의존성 주입으로 전환한다. `Platform.CurrentPlatform` 대신 `_platformType`(생성자 주입) 필드로 캐싱하고, 입력 장치 기능 쿼리(키보드 포커스, 키 반복) 역시 초기화 시점에 `_inputCapabilities` 같은 설정 객체로 캡슐화한다. GlobalState 56을 10 이하로 줄이되, 플랫폼 전환(게임 런타임 중 드물게 발생)이 필요하면 캐시 무효화 콜백을 도입한다.
  • 입력 이벤트 로직에서 UI 상태 변이(SelectionStart, SelectionEnd, Text 변경)를 분리된 private 메서드로 격리한다. `HandleKeyPress` → 키 해석 → `ApplyTextModification(startPos, endPos, newChar)` 같은 순결한 인터페이스로 전환하면, 입력 시뮬레이션 테스트와 성능 프로파일링이 용이해진다.

테스트 우선순위

  • **Characterisation Test (입력 이벤트 oracle)** — 현재 `HandleKeyPress`의 각 주요 키(RETURN, TAB, ESCAPE, BACKSPACE, HOME, END, Ctrl+A, Ctrl+C, Ctrl+V 등) 입력에 대한 상태 변화(Text, SelectionStart, 콜백 호출 여부)를 golden master로 기록한다. 이후 리팩토링 후 동일한 입력에 대해 출력이 변하지 않음을 검증하는 regression test 기반 확보.
  • **Platform-specific Behavior Unit Test** — OSX vs Linux/Windows의 입력 해석 차이(Cmd+C vs Ctrl+C 등)를 별도 테스트로 분리하되, 실제 `Platform.CurrentPlatform` 싱글톤 대신 mock/stub 주입으로 각 플랫폼 분기를 독립 검증한다. 이를 통해 dispatch 테이블 리팩토링 후 플랫폼 조건부 로직이 정확히 작동함을 보장한다.
  • **Performance Regression Test (핫 패스 성능)** — `HandleKeyPress` 메서드의 실행 시간(마이크로초 단위)을 벤치마크 하고, 리팩토링(dispatch 테이블 도입, 캐싱) 후 성능이 현재 대비 10% 이상 저하되지 않았는지 자동 검증한다. 매 프레임 호출되는 메서드이므로 누적 GC 압력 증가도 모니터링 대상이다.
불확실성: 코드 스니펫이 부분 표시(truncated, lines 210-469)되어 전체 메서드 본문을 확인하지 못했으므로, 실제 CC 98이 어느 구간에 집중되어 있는지(단일 거대 switch 대 여러 중첩 if-else 대 다중 메서드 호출) 확실하지 않다. 또한 `OnEnterKey`, `OnTabKey`, `OnEscKey` 같은 콜백 메서드들이 이 클래스 내부에서 선언되었는지 외부에서 주입되는지 불명확하며, 만약 이들이 외부 이벤트 핸들러라면 dispatch 테이블 설계가 달라질 수 있다. `Platform.CurrentPlatform` 접근 56회는 클래스 전체 메서드 평균이므로, `HandleKeyPress` 단일 메서드 내 접근 빈도는 더 낮을 가능성도 있다.

위험 원인
