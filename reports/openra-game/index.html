Game Spaghetti Index (G-SI)는 게임 코드의 각 클래스가 다른 코드와 얼마나 얽혀 있는지를 0~100점으로 측정한 지표입니다. 점수가 높을수록 위험합니다.

등급 의미 → A 안전 · B 일반 · C 보통 · D 리팩토링 후보 · E 심각

💡 각 섹션 제목 옆의 「ⓘ 이 섹션이 뭔가요?」 버튼을 누르면 그 섹션이 무엇을 보여주는지 자세한 설명이 나옵니다. 화면 곳곳의 항목에 마우스를 올리면 그 자리에서 짧은 설명이 풍선으로 표시됩니다.

Project Health

이 프로젝트의 스파게티 정도를 한 숫자로 답하는 종합 점수입니다. 0~100 점, 점수가 높을수록 코드가 전반적으로 엉켜 있다는 뜻입니다.

다음 네 가지 신호를 가중 평균합니다.

  • 평균 G-SI (45%) — 프로젝트 안 모든 클래스의 G-SI 점수를 단순 평균. 가장 큰 비중.
  • 위험(D+E) 비율 (25%) — G-SI 60 이상(=D 등급 이상)인 클래스가 전체에서 차지하는 비율을 0~100 점으로 환산.
  • 순환 의존성 수 (15%) — A→B→C→A 처럼 서로 참조해서 빙빙 도는 묶음의 개수. 로그 스케일 적용(0 → 0점, 1 → 30점, 5 → 70점, 20 이상 → 100점).
  • 평균 결합도 (15%) — 클래스 한 개당 평균적으로 몇 개의 다른 클래스와 연결되는지(fan-in+fan-out 평균). 평균 10 이상이면 100점으로 saturate.

등급 기준은 다른 점수와 동일하게 A(0~19) · B(20~39) · C(40~59) · D(60~79) · E(80~100) 입니다. 발표 슬라이드에 "이 프로젝트는 C 등급(47점) — 평균 수준의 코드베이스" 같은 한 줄 요약으로 쓰기 좋은 숫자입니다.

Summary

분석 규모와 위험 신호를 6개 숫자로 압축한 카드 묶음입니다.

  • 분석 클래스 — Roslyn으로 파싱한 class · struct · interface · record · enum의 총 개수.
  • 분석 메서드 — 분석된 모든 메서드와 생성자(.ctor)의 합. enum 항목, 자동 속성은 카운트하지 않습니다.
  • 의존성 순환(SCC ≥ 2) — 크기가 2 이상인 강한 연결 요소(Strongly Connected Component). 적을수록 좋고, 0이면 의존성이 한 방향으로 흐른다는 좋은 신호입니다.
  • 평균 G-SI — 클래스 단위 G-SI 점수의 단순 평균. Project Health의 가장 큰 입력입니다.
  • 최대 G-SI — 이 프로젝트에서 가장 위험한 한 클래스의 G-SI. 보통 95~100점이 나옵니다 (percentile rank 특성상).
  • 위험(D/E) 클래스 — G-SI 60 이상인 클래스의 수. 변경할 때 영향 분석과 테스트 보강이 필요한 클래스들입니다.

등급 분포 및 가중치

왼쪽 등급 분포 차트는 프로젝트 안의 모든 클래스를 등급별로 나눠 비율을 보여줍니다. G-SI 점수는 프로젝트 내부의 분포에서 percentile rank로 계산하므로, 다섯 등급(A~E)이 각각 약 20% 씩 거의 균등하게 분포하는 것이 정상입니다.

이 차트가 의미하는 것은 절대적인 위험도가 아니라 "이 프로젝트 안에서의 상대적 위치"입니다. 다른 프로젝트와 직접 비교하려면 raw 점수 분포(평균 G-SI, 최대 G-SI 등)를 함께 봐야 합니다.

오른쪽 표는 G-SI 산식에서 각 항목이 어느 정도 비중으로 가중 평균되는지 정리한 것입니다. 각 항목 이름에 마우스를 올리면 무엇을 측정하는지 한국어 설명이 풍선으로 나타납니다. 본 작품은 default 가중치로 산식의 신뢰도를 확보하고, 후속 단계에서 데이터 기반 튜닝(--weights tuned) 옵션을 추가할 예정입니다.

Hotspot Table (G-SI 상위)

위험한 순서로 정렬된 클래스 목록입니다. 기본은 전체 클래스 중 G-SI 상위 N개를 보여주며, 두 가지 방법으로 표를 좁힐 수 있습니다.

  • 등급 필터 — A~E 중 하나를 선택하면 그 등급 안에서 다시 상위 N개를 골라 표를 새로 그립니다. "B 등급 안에서 가장 위험한 30개"처럼 봅니다.
  • 텍스트 검색 — 클래스의 정규 이름(FQN)이나 파일 경로 일부를 입력하면 일치하는 클래스만 남깁니다. 등급 필터와 동시 적용 가능합니다.

컬럼별 의미 — 헤더에 마우스를 올리면 각 컬럼이 무엇을 측정하는지 설명이 표시됩니다. 컬럼 헤더를 클릭하면 그 항목 기준으로 정렬됩니다(다시 누르면 역순). 우측 카운터는 "현재 보이는 행 수 / 조건을 만족하는 전체 / 프로젝트 전체"를 보여줍니다.

주요 원인 컬럼은 G-SI 점수에 가장 크게 기여한 두 항목을 알려 줍니다. 예를 들어 "cc, global_state" 는 그 클래스가 분기가 많고 전역 상태에 강하게 의존한다는 뜻입니다.

기본은 전체 클래스 중 G-SI 상위 30개를 표시합니다. 특정 등급(A~E)을 선택하면 그 등급 안에서 상위 30개를 다시 보여줍니다. 전체 등급 분포는 위 등급 분포 차트에서 확인하세요.

Dependency Graph (G-SI 상위 hotspot 중심)

위험 클래스 주변의 참조 관계를 점과 선으로 그린 그래프입니다.

  • 점(노드) = 클래스. 색은 등급(A 녹색 ~ E 빨강), 크기는 결합도(다른 클래스와 연결된 정도)에 비례합니다.
  • 선(엣지) = 한 클래스가 다른 클래스를 참조하는 의존성. 화살표 방향은 "이 클래스를 사용한다"의 방향입니다.
  • 표시 범위 — G-SI 상위 hotspot 부터 채우고 그 인접 클래스까지 포함하되, 노드 수가 최대 150개를 넘지 않도록 제한합니다. 그래서 작은 프로젝트는 그래프 전체가, 큰 프로젝트는 가장 위험한 영역만 표시됩니다.
  • A · B 등급 노드가 보이지 않는 이유 — 그래프 자체가 위험 클래스 중심으로 그려지기 때문에 표시 범위 안에는 거의 D · E 등급(과 일부 C)만 포함됩니다. A · B 클래스는 위 등급 분포 차트와 Hotspot Table 등급 필터에서 확인하세요.

Cycle Explorer (Strongly Connected Components)

A → B → C → A 처럼 서로 참조해서 빙빙 도는 클래스 묶음(Strongly Connected Component, SCC)을 모은 섹션입니다.

일반적으로 의존성은 한 방향으로 흘러야 합니다(예: UI → 로직 → 데이터). 그런데 두 클래스가 서로를 참조하기 시작하면, 한쪽을 수정할 때 반드시 다른 쪽도 함께 신경 써야 합니다. 이런 묶음이 3개, 4개로 커지면 영향 범위 추적이 사실상 불가능에 가까워집니다. 그래서 SCC는 리팩토링 1순위 후보입니다.

본 섹션의 카운트 카드 숫자가 곧 프로젝트 안의 모든 SCC 수입니다. 상위 N개를 보여주는 것이 아니라 전부 나열합니다. 프로젝트마다 수치가 다른데, 예를 들어 OpenRA.Game 모듈은 5개, OpenRA.Mods.Common 모듈은 4개의 묶음이 있습니다.

각 항목을 클릭하면 그 묶음에 속한 클래스 FQN 목록이 펼쳐집니다. 묶음 안의 모든 클래스가 동일한 SCC에 있다는 사실 자체가 이미 위험 신호이므로, 점수가 낮은 클래스라도 함께 정리 대상이 됩니다.

Module Summary

클래스 단위로 계산된 G-SI 점수를 최상위 폴더(모듈) 단위로 집계한 표입니다. "이 폴더 안 클래스들이 평균적으로 얼마나 위험한가"를 한눈에 봅니다.

컬럼 의미

  • 모듈 — 분석 입력 폴더 바로 아래의 1단계 폴더 이름. 예를 들어 OpenRA.Game을 분석하면 Network, Server, Map 등이 모듈로 잡힙니다. (root)는 폴더 안에 들어있지 않고 분석 폴더 바로 밑에 놓인 .cs 파일들을 한 모듈로 묶은 것입니다.
  • 등급 — 모듈 내 클래스 평균 G-SI를 기준으로 한 A~E 등급.
  • 평균 G-SI — 모듈에 속한 모든 클래스의 G-SI 평균. 모듈 전체의 위험도를 가장 잘 대표하는 값입니다.
  • 최대 G-SI — 모듈에서 가장 위험한 클래스 하나의 G-SI. 평균은 낮은데 최대만 높다면 그 모듈에 핀포인트 hotspot이 있다는 신호입니다.
  • 파일 수 · 클래스 수 — 모듈에 속한 .cs 파일과 클래스(struct, interface, record 포함)의 개수.

모듈 단위로 보면 어느 컴포넌트가 통째로 정리 대상인지, 아니면 특정 클래스만 문제인지 빠르게 판단할 수 있습니다.

각 카드는 G-SI 상위 hotspot 한 개에 대한 LLM 의 정성 분석입니다. 카드를 클릭하면 펼쳐집니다. 각 카드는 다음 네 섹션으로 구성됩니다.

  • 위험 원인 — 왜 이 코드가 위험한지. 지표 수치(CC, 결합도, SCC 크기, GlobalState)를 직접 인용합니다.
  • 리팩토링 방향 — 게임 도메인 맥락(게임 루프 핫 패스, god-object, 거대 switch 등)을 반영한 구체적 제안. 코드를 직접 만들지는 않습니다 (plan §6.4).
  • 테스트 우선순위 — 안전한 변경을 위해 먼저 작성·강화할 테스트. characterisation test / golden master / performance regression 같은 게임·레거시 코드 적합한 유형을 권고합니다.
  • 불확실성 — 모델이 명시한 추측 한계. 의존성 그래프 일부만 봤다거나 스니펫이 짧다거나 등.

본 가이드는 의사결정 보조용 입니다. 실제 리팩토링은 사람이 의존성 그래프와 영향 범위를 직접 확인한 뒤 진행해야 합니다.

위험 원인

  • 매우 높은 순환 복잡도(CC 93.0)로 인해 메서드 내 제어 흐름이 극도로 복잡함. ProcessOrder 메서드는 거대 switch 구조로 40개 이상의 order 타입을 다루며, 각 case 내에서 다중 조건문과 중첩 루프를 포함하고 있어 테스트 경로 수가 2^93 에 가까워 완전 커버리지가 불가능함.
  • 전역 상태 접근(GlobalState 47)이 매우 높음. TextNotificationsManager, OrderManager, World 같은 싱글톤형 static 인스턴스를 직접 참조하고 있으며, 이들은 순수 함수 테스트를 불가능하게 만들고 게임 루프 내 상태 추적을 어렵게 함.
  • 게임 루프 중심성(GameLoopCentrality 0.3333)이 상당함. ProcessOrder는 network message 처리 핫 패스에서 매 프레임 호출될 수 있으며, 여기서 발생하는 예외나 지연은 네트워크 응답 지연으로 직결되어 게임 플레이 경험에 즉시 영향을 미침.
  • 소규모 fan-out(5개)이지만 각 의존 클래스(Order, MiniYaml, FluentMessage 등)는 네트워크 메시지 파싱 및 게임 상태 동기화의 핵심이므로, 이 메서드의 변경은 멀티플레이어 동작 전체에 영향을 미칠 수 있음.

리팩토링 방향

  • giant switch 를 Strategy/Command 패턴으로 분해. 각 order 타입별로 별도 handler 클래스를 도입하되, handler 자체는 현재 큰 switch 문을 소유하지 말고 OrderType → Handler mapping 딕셔너리로 관리. 이렇게 하면 CC를 메서드당 10~15 로 낮출 수 있고, 새 order 타입 추가 시 기존 switch 문을 수정하지 않아도 됨.
  • Global state 의존성을 제거하기 위해 OrderProcessor 를 생성자 주입 가능한 service 로 변환. TextNotificationsManager, OrderManager 의 참조를 static 호출 대신 생성자 파라미터로 받도록 시그니처를 변경. 게임 루프 초기화 시 한 번만 의존성을 설정하므로 성능 오버헤드 없음.
  • ProcessOrder 내에서 order 검증 / 파싱 / 상태 적용 을 three-phase 로 분리. validation phase 에서 미리 잘못된 order 를 reject 하고, parsing phase 에서는 pure function 으로 order → domain object 변환, application phase 만 side-effect 수행. 각 phase 를 별도 메서드로 추출하면 unit test 와 integration test 를 명확히 분리할 수 있음.
  • 고위험 case 그룹(Player action orders: Move, Attack, Build 등)을 별도 클래스로 먼저 추출해 점진적 리팩토링 시작. 반드시 필요한 handler 만 먼저 분리하고, 시스템 메시지(Message, FluentMessage) 같은 낮은 변경 빈도 case 는 당분간 switch 에 남겨두어 리팩토링 범위를 한정.

테스트 우선순위

  • ProcessOrder 의 각 order 타입별 characterisation test (golden master) 작성. 현재 코드 행동을 .yaml/.json snapshot 으로 기록하고, 리팩토링 후 동일한 네트워크 패킷 입력에 대해 같은 결과를 내는지 regression 검증. 멀티플레이어 시나리오(join, leave, unit order, resource transfer 등) 를 20~30 개 케이스로 정의.
  • Pure function 테스트 (validation + parsing phase). order 문자열을 입력으로 받아 정상/에러 상태를 돌려주는 메서드를 별도로 만들고, mocking 없이 즉시 테스트 가능하게 함. 특히 malformed order(missing field, invalid value, boundary cases) 에 대해 30+ 케이스 검증.
  • Performance regression test. ProcessOrder 를 10,000 회 호출하는 benchmark 를 작성하고, 리팩토링 전후 평균 응답 시간 및 GC allocation 을 측정. 게임 루프 핫 패스이므로 1% 이상의 성능 저하도 허용 불가.
  • Integration test (OrderManager + World + TextNotificationsManager 통합). network message 를 받아 order 가 올바르게 world state 에 반영되고 UI notification 이 발생하는지 검증. 멀티플레이어 상황(2~4 player) 에서 메시지 순서 섞임, 지연 등 edge case 포함.
불확실성: 코드 스니펫이 일부만 제공되었으므로, 전체 40+ case 의 정확한 분포(데이터 처리 case vs 상태 변경 case vs UI-only case)를 확인할 수 없음. ProcessOrder 메서드의 총 라인수가 368 라인(48~415)인데, 한 메서드가 이렇게 크다는 것 자체가 극도로 높은 CC 를 뒷받침함. 또한 global state 접근 47 건이 주로 ProcessOrder 메서드에 집중된 것인지, 클래스 내 다른 static initializer 나 helper method 에 분산된 것인지 불명확함. 게임 루프 중심성 0.3333 은 상당히 높지만, 이것이 network thread 에서 호출되는지 main game thread 에서 호출되는지 확인 필요. 만약 background thread 라면 static state 접근에 concurrent modification risk 가 있을 수 있음.

  • **세션 관리 / 플레이어 추적을 Strategy 패턴으로 분리**: `PlayerMessageTracker`, `OrderBuffer` 등 관련 클래스들이 이미 분리되어 있으나, Server 클래스에서 이들을 직접 생성/소유하고 있다. 세션 라이프사이클(생성→활성→종료)을 `ISessionManager` 인터페이스로 추상화하고, dependency injection 으로 주입받도록 변경하면 coupling 을 낮출 수 있다. 특히 테스트에서 mock SessionManager 로 교체 가능해진다.
  • **전역 상태 의존성을 명시적 컨텍스트 인자로 치환**: GeoIP, Settings 같은 정적 접근을 추적하고, 가능한 한 Server 생성자 또는 메서드 인자로 주입받도록 점진적으로 변경한다. 예를 들어 `GeoIP.LookupCountry(ipAddress)` 호출을 `this.geoipService.LookupCountry(ipAddress)` 로 변경한다. 이는 GlobalState 176 을 단계적으로 낮추며, 테스트 환경에서 mock GeoIP 사용을 가능하게 한다.
  • **ValidateClient 의 거대 메서드 분해**: 현재 240줄 이상의 메서드를 5~6개의 작은 유효성 검사 단계로 분해한다 (예: `ValidateGameState()`, `ValidateCredentials()`, `ValidatePlayerInfo()`, `ValidateSlots()`, `CreateAndRegisterSession()`). 각 단계마다 조기 반환(early exit)을 사용하면 CC 를 단계별로 낮출 수 있고, 테스트도 단위별로 가능해진다. 이미 `DropClient()`, `SendOrderTo()` 헬퍼가 있으므로 패턴 일관성도 유지된다.
